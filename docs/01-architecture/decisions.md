# Architecture decisions

ADR-style records, short on purpose. All are Proposed until Gate 1. Each one names the alternatives we rejected and why, so a later reader can tell whether the reason still holds. New decisions get appended. A changed decision gets a new record that supersedes the old one; old records are never edited.

---

### ADR-001: One Next.js app and one Supabase project

- Status: Proposed, 2026-11-09
- Decision: A single Next.js (App Router) app with route groups for guest, staff, admin and platform, deployed on Vercel, on top of one Supabase project. No separate API service, no queue product, no microservices.
- Rejected: separate apps per surface (four deploys and duplicated auth for one small team); a NestJS API like nodedr (a second runtime to host and secure, when Postgres functions plus server actions cover it); a self-hosted LAN server like FloCafe (needs hardware and IT in every café).
- Consequences: One codebase, one deploy, shared types. Route-group boundaries must be respected, so the guest bundle never imports admin code (checked in Phase 2 with bundle analysis).

### ADR-002: Shared schema, `restaurant_id` on every row, RLS plus composite tenant keys

- Status: Proposed
- Decision: All tenants share tables. Isolation is enforced by RLS on every table and by composite foreign keys `(restaurant_id, parent_id)`.
- Rejected: a schema per tenant (migrations × tenants, and connection pooling gets awkward); a database per tenant (cost and operations far beyond 10,000–20,000 AMD per month per café); application-level filtering only (nodedr's approach; one missed `where` leaks a café).
- Consequences: One migration path. Every new table needs `restaurant_id`, RLS and policies. CI checks that RLS is on and runs the cross-tenant tests.

### ADR-003: Restaurant is the tenant, location is the billing unit

- Status: Proposed
- Decision: `restaurants` own menus, staff and branding. `locations` own tables, stations, counters, the published menu and the subscription.
- Rejected: location as tenant (chains would duplicate menus and staff); restaurant-level billing (the business model is per location).
- Consequences: Menus are shared and assigned to locations (`menu_locations`). Prep areas are per restaurant; stations are per location.

### ADR-004: Clients read through RLS, state changes go through Postgres functions

- Status: Proposed
- Decision: Browsers query tables directly for reads. Plain forms (menu, floor, settings) write directly under RLS. Orders, tickets, sessions, bills and payments change only through `api.*` functions, which assert the caller's role at that location (guest functions included since ADR-038). Clients have no `INSERT/UPDATE/DELETE` grants on those tables.
- Rejected: all writes through Next.js server actions with the service role (RLS stops protecting writes, and one bug becomes a cross-tenant write); all writes as plain table updates under RLS (pricing, fan-out and transitions can't be expressed in policies).
- Consequences: The rules are tested in SQL (`90-smoke-test.sql`, then pgTAP or Vitest in CI). `SECURITY DEFINER` functions follow strict rules: `search_path = ''`, an explicit role assert, an explicit `revoke … from public, anon, authenticated`.

### ADR-005: Guests are Supabase anonymous users; guest writes go through our server

- Status: Accepted for anonymous guests; the server-and-service-role part is superseded by ADR-038
- Decision: The guest's first action (order, call waiter) silently creates a Supabase anonymous session behind invisible Turnstile. Reads (their orders, their Realtime channel) use that JWT under RLS. Writes go through a server action that verifies the table QR and the JWT, then calls `private.join_table` and `private.place_guest_order` with the service role.
- Rejected: no auth at all, with order status by unguessable URL and public channels (no RLS, and Realtime would need "public access" switched on project-wide); custom JWTs signed by us (fights Supabase's key management); guest sign-up (kills ordering).
- Consequences: The anonymous sign-in limit must be raised from 30 to about 300 per hour per IP, because café guests share one IP. Anonymous users need a cleanup job. Stage 3 and 4 can upgrade a guest to a real customer with identity linking and keep their history.

### ADR-006: Table QR is an HMAC-signed static token with key id and per-table version

- Status: Proposed
- Decision: `/t/<token>`; the token holds a format byte, key id, table id, `qr_version` and a 96-bit HMAC-SHA256 tag. Verified on the server before any database work. Reprinting one table bumps `qr_version`; rotating the key uses `kid`.
- Rejected: a random token stored hashed (equally safe, but every garbage request costs a database lookup, and the brief asked for signed tokens); codes that rotate daily (needs a screen or reprinting every day); NFC tags (hardware cost).
- Consequences: A photographed sticker still works off-site. Damage is limited by waiter acceptance above a threshold, table-empty flags and reprinting (`multi-tenancy-and-security.md`).

### ADR-007: Three state machines, one derived guest status

- Status: Proposed
- Decision: `orders.status` (placed, accepted, rejected, cancelled), `kitchen_tickets.status` per station (new, cooking, ready, served, cancelled) and the bill/payment state are separate. `orders.kitchen_status` (slowest live ticket) is kept by a trigger. The guest-facing status comes from `order_display_status()`: received → accepted → cooking → ready → served → paid.
- Rejected: one big status column (it can't express "paid but still cooking" or "bar ready, kitchen cooking", and nodedr and FloCafe both split it for this reason); fully configurable statuses like TastyIgniter (the kitchen screen and analytics can't reason about them).
- Consequences: Transitions are compare-and-set functions with role checks. Every change is logged to `order_status_history`.

### ADR-008: An order is an immutable round inside a table session

- Status: Proposed
- Decision: A `table_session` is the open check (one per table at a time). Each submission by a guest or waiter is a new `order` in it. Orders aren't edited after placement; lines can only be cancelled.
- Rejected: one mutable order per table that grows (edits conflict between a guest phone, the waiter tablet and an offline outbox; tickets would need diffs, which is URY's fragile part).
- Consequences: Offline replay is safe. Bills cover a session. Stage 2 split bills split session lines across several bills.

### ADR-009: Station routing through prep areas; kitchen tickets never change

- Status: Proposed
- Decision: Items or categories declare a prep area (Kitchen, Bar). Each location maps prep areas to its stations, with a default station as fallback. An order fans out into one ticket per station. A cancellation after cooking starts creates a `void` ticket that the kitchen must acknowledge.
- Rejected: routing by item group only, as in URY (no per-item override); a `station_id` on items (breaks for chains whose locations have different screens); editing tickets in place (cooks miss changes).
- Consequences: Setup needs a prep-area-to-station screen. A one-screen café maps everything to the default station, so it's zero effort.

### ADR-010: Realtime is Broadcast from the database to private channels, used as hints

- Status: Proposed
- Decision: Triggers call `realtime.send()` to `loc:<location>` and `guest:<guest_session>`. Access is controlled by RLS on `realtime.messages`, and clients can't send. Clients refetch on every message, on every reconnect and on a 10–15 s safety poll.
- Rejected: Postgres Changes (Supabase recommends Broadcast for scale and security, and Postgres Changes checks RLS per subscriber per change); Socket.IO on our own server (another service to run); polling only (misses the 2-second target).
- Consequences: Payloads stay tiny. Correctness never depends on receiving every message.

### ADR-011: Server-authoritative offline handling with a staff outbox

- Status: Proposed
- Decision: Waiter and kitchen PWAs queue safe actions (orders with idempotency keys, compare-and-set status changes) in IndexedDB and replay them in order. A stale conflict drops the action and refetches. Money, publishing and post-service cancellations are never queued. Guests retry with an idempotency key.
- Rejected: a local-first sync engine (PowerSync, ElectricSQL, RxDB): a big dependency and real conflict resolution for a problem that short, safe queues solve; no offline support (cafés would lose orders in every drop).
- Consequences: Every queued action has to be idempotent in the database; the smoke test covers it. The UI must show pending actions honestly.

### ADR-012: Money is integer AMD

- Status: Proposed
- Decision: Every price and total is an `integer` count of whole drams. The single currency is `AMD`, enforced by a check constraint. The conversion to the decimal format a payment provider wants (Ameria: `25000.00`) happens at the provider boundary only. Stage 4 ingredient costs are `numeric`.
- Rejected: floats (eatlah); text (menufic); minor units (luma aren't used in practice, so `150000` for 1,500 AMD invites bugs).
- Consequences: No rounding inside the app. Adding a currency with real minor units later would need a migration.

### ADR-013: Translations as rows; published menus and order lines as snapshots

- Status: Proposed
- Decision: Five `*_translations` tables with `source` and `reviewed_at` per row. Publishing builds an immutable `menu_versions.snapshot` per location. Order lines copy `name_i18n` in all three languages.
- Rejected: `name_en`-style column pairs (eatlah; doesn't scale to three languages and has nowhere to store review state); a JSONB `{hy, ru, en}` column per entity (simpler queries, but no per-language review metadata); one generic polymorphic translation table (no foreign keys).
- Consequences: The editor joins translation tables. Guests and waiters read one JSON document, which is fast and cacheable. The kitchen reads its own language from order lines.

### ADR-014: Unreviewed AI output can't be published, enforced in the database

- Status: Proposed
- Decision: Rows written from AI output are `source = 'ai'`. `api.publish_menu` raises `unreviewed_ai_translations` while any of them at that location lacks `reviewed_at`.
- Rejected: a check in the UI only (bypassable, and easy to break in a refactor).
- Consequences: The review screen has to make reviewing fast: approve per item, per category, or "all looks right" after scrolling through.

### ADR-015: Our own formatters for numbers and dates

- Status: Proposed
- Decision: A small shared module formats AMD, numbers, dates and times for hy, ru and en. Plurals use `Intl.PluralRules` through next-intl.
- Rejected: relying on `Intl` (Chromium has no Armenian number, date or list data and silently prints English; checked on 9 Nov 2026).
- Consequences: About a hundred lines of code with unit tests. One consistent price format everywhere (`1 500 ֏`).

### ADR-016: Telegram and other side effects go through an outbox

- Status: Proposed
- Decision: The order transaction inserts into `notification_outbox`. Delivery happens through `pg_net` → `/api/jobs/notify`, with a `pg_cron` retry sweep every minute and dead-lettering after 8 attempts.
- Rejected: calling Telegram inside the server action (a slow or failed Telegram call would block or lose orders); a queue service (another vendor for a few messages per minute).
- Consequences: Alerts arrive seconds after the order, not milliseconds. Failures are visible and retried.

### ADR-017: Stage 1 staff devices pair with a code; personal staff logins come in Stage 2

- Status: Proposed
- Decision: Kitchen screens and shared waiter tablets are paired with a 10-minute, single-use code and become `kind = 'device'` members. Owners and managers have personal email logins.
- Rejected: personal accounts for every waiter in Stage 1 (email or SMS for every waiter slows onboarding below the 30-minute target); one shared password per café (no revocation, no audit).
- Consequences: Stage 1 can't attribute sales to individual waiters. Stage 2 adds PINs on shared devices (`members.pin_hash`) for per-waiter stats.

### ADR-018: Sizes and options are modifier groups

- Status: Proposed
- Decision: Reusable `modifier_groups` with `min_select` and `max_select`. A size is a required group with min = max = 1.
- Rejected: a separate variants table (two concepts for the same UI; nodedr lacks variants and is fine).
- Consequences: One pricing path in `place_order_core`. Group rules are validated on the server; the smoke test covers it.

### ADR-019: Frankfurt for the database and the server

- Status: Proposed
- Decision: Supabase `eu-central-1` and Vercel functions in `fra1`.
- Rejected: split regions (every server action would pay a database round trip across regions); regions further from Yerevan.
- Consequences: Yerevan-to-Frankfurt latency has to be measured from a real café in Phase 4 to confirm the 2-second kitchen target.

### ADR-020: Rate limits in Postgres and at the edge, no Redis

- Status: Proposed
- Decision: Per-guest, per-table and per-order limits live in an unlogged Postgres counter table. Per-IP limits use the Vercel Firewall, plus Turnstile before anonymous sign-in.
- Rejected: Upstash or other Redis (another vendor and secret before we have traffic that needs it).
- Consequences: Revisit if `private.rate_limits` shows up in slow-query logs.

### ADR-021: Stage 3 payments use the hosted page, server-side verification and per-location credentials in Vault

- Status: Proposed
- Decision: For Ameriabank vPOS (or ArCa EPG): the server calls InitPayment, the guest goes to the bank's hosted page, and the server checks the result with GetPaymentDetails. We never trust the redirect. A reconciliation job covers guests who never come back. Each location's credentials sit in Supabase Vault. Every attempt has a new integer OrderID (`payment_attempts`).
- Rejected: trusting BackURL parameters (Ameria signs nothing and has no webhook); storing credentials in tables or env vars per tenant.
- Consequences: Each café probably needs its own merchant contract. A platform or sub-merchant deal with one bank would simplify onboarding. Phase 5 left this for Stage 3: Stage 1 takes no guest payments, and cafés pay us by invoice (`docs/05-business/pricing.md`).

### ADR-022: Fiscal receipts (HDM) are out of scope until we have tax advice

- Status: Proposed
- Decision: Stage 1 prints nothing and handles no money beyond recording how a table paid. The café keeps its existing HDM. Before Stage 2 printing, an Armenian tax adviser answers what a POS that prints bills must do.
- Rejected: designing an HDM integration now (rules unknown; risk of building the wrong thing).
- Consequences: Stage 2 has a hard dependency on that answer. Our printed bills must never look like fiscal receipts.

### ADR-023: UUID v4 keys and Postgres enums for states

- Status: Proposed
- Decision: `uuid` primary keys (`gen_random_uuid()`, clients can generate them too). `enum` types for statuses and roles. People see numbers only where they need them: per-day order and bill numbers.
- Rejected: bigint identities (clients can't create ids offline, and they leak volume); text with check constraints for states (no generated TypeScript union types).
- Consequences: Enum values can be added but not removed, so new states need care. Fine for state machines that rarely change.

### ADR-024: Guests use Realtime until about 15 cafés, then we revisit

- Status: Proposed
- Decision: Guests subscribe to `guest:<session>` while an order is open. At about 15 live cafés we either lift the Pro plan's 500-connection cap (spend cap off, 10,000) or switch guests to 10-second polling.
- Rejected: deciding now without real connection numbers.
- Consequences: `costs.md` (Phase 4) prices both paths. The guest client hides the transport behind one hook, so switching is a small change.

## Phase 2 decisions

### ADR-025: Free plans only until the owner says otherwise

- Status: Accepted (owner instruction), 2026-11-09
- Decision: Use only free plans and services. AI runs on the Gemini free tier, the database on Supabase Free, hosting on Vercel Hobby, monitoring on free tiers. Anything that needs money stops and goes to the owner.
- Consequences:
  - Vercel Hobby allows only personal or non-commercial use. It's fine for building and a free pilot, but paid hosting is needed before the first café pays.
  - Supabase Free has no backups, so a nightly encrypted `pg_dump` runs in GitHub Actions. Projects pause after a week without activity, and 200 Realtime connections cap the pilot at roughly 8 busy cafés.
  - Gemini's free tier may use prompts to improve Google's products. Menu photos are public information; owners are told at import.
  - Vercel Hobby allows one firewall rate-limit rule. It goes on `/t/*`; everything else relies on the Postgres limits.
  - Upgrade order when lifted: Supabase Pro → paid hosting → Claude → email domain.

### ADR-026: The AI menu reader sits behind our own interface, on official SDKs

- Status: Proposed
- Decision: A `MenuReader` interface (`readMenu`, `translate`) with a Gemini adapter (`@google/genai`) and a Claude adapter (`@anthropic-ai/sdk`). Both return data validated by one Zod schema. `AI_PROVIDER` picks the adapter.
- Rejected: Claude only (not free); the Vercel AI SDK (`ai` 7) as a provider abstraction (more surface than two calls need, and it hides provider-specific structured-output features).
- Consequences: The Phase 6 test set (15–20 real menus) runs against Gemini now and against Claude once allowed, so the switch is measured, not assumed.

### ADR-027: `uqr` plus our own SVG for table QR codes

- Status: Proposed
- Decision: Generate the QR matrix with `uqr` 0.1.3 (no dependencies) and render the branded SVG and A4 print sheets ourselves, using print CSS.
- Rejected: `qr-code-styling` 1.9.2 (last release April 2025, browser-canvas oriented); a PDF library (the browser prints A4 well).
- Consequences: We own about 100 lines of SVG drawing. QR codes must use high error correction when a logo covers the centre; tested by scanning printed sheets with real phones in Phase 6.

### ADR-028: Charts with Recharts through shadcn, not Tremor

- Status: Proposed
- Decision: `recharts` 3.10.1 via shadcn's chart component, styled with our tokens.
- Rejected: `@tremor/react` (last published January 2025; its successor is copy-paste code on Recharts anyway).

### ADR-029: A hand-written service worker, no PWA library

- Status: Proposed
- Decision: `public/sw.js` with cache-first for hashed `/_next/static` files, network-first for staff pages with an offline fallback, plus `idb` for the outbox. The manifest comes from `app/manifest.ts`.
- Rejected: `@serwist/next` (adds `@serwist/cli`; precaching every route isn't needed).
- Consequences: Service-worker updates are versioned by hand; Playwright tests the offline path.

### ADR-030: Restaurant OS gets its own Supabase project; the existing one is off limits

- Status: Proposed
- Decision: Create `restaurant-os-dev` (free, `eu-central-1`) in Phase 6 after the owner confirms. Production gets its own project when the free rule allows. The account's existing project "Exishe's Project" is never used.
- Rejected: reusing the existing project (it holds another product's tables, and our migrations revoke default grants across `public`, which would break that product).
- Consequences: It uses the second of the two free project slots.

### ADR-031: TypeScript 6 and ESLint 9 until the ecosystem catches up

- Status: Proposed
- Decision: Pin `typescript` 6.0.3 and `eslint` 9.39.5.
- Rejected: TypeScript 7.0.2 (outside `typescript-eslint`'s supported range `<6.1.0`); ESLint 10 (three plugins inside `eslint-config-next` 16.4.5 accept ESLint up to 9).
- Consequences: Revisit when `typescript-eslint` and `eslint-config-next` release support. Dependabot will flag the upgrades.

### ADR-032: npm and exact version pins

- Status: Proposed
- Decision: npm with a committed `package-lock.json` and exact versions in `package.json`. Upgrades arrive as pull requests that must pass CI and the license allowlist.
- Rejected: pnpm (fine, but the supply-chain auditor we use doesn't read its lockfile).

## Phase 4 decisions

### ADR-033: Operational safeguards found by walking through a Friday evening

- Status: Proposed, 2026-11-09
- Decision: Add to Stage 1:
  1. Possible duplicates: a QR order with the same dishes as another order from the same table within 3 minutes, from a different guest session, waits for the waiter instead of going straight to the kitchen.
  2. "Kitchen busy": a switch with an expected wait (20/30/45 min) shown to guests, which turns off by itself after an hour.
  3. Device heartbeat: an alert to the owner when a kitchen or bar screen is offline for 2 minutes during opening hours.
  4. Stale-table guard: a new guest joining a table whose orders are all served and whose bill was requested (or idle for 45 minutes) makes the waiter close the old bill first.
  5. Test orders: an `is_test` flag that keeps onboarding and training orders out of sales reports.
- Rejected: blocking all second orders from a table (punishes real second rounds); estimating wait times automatically (not enough data in Stage 1; the cook knows better).
- Consequences: Schema additions in the Stage 1 migrations are:
  - `locations.kitchen_busy_until` and `locations.expected_wait_minutes`;
  - `members.last_seen_at`;
  - `orders.is_test`;
  - a `possible_duplicate_of` reference on orders.
    `day-in-the-life.md` has the scenarios behind each one.

### ADR-034: Frankfurt confirmed by measurement

- Status: Accepted, 2026-11-09
- Context: ADR-019 chose Frankfurt before latency from Armenia was measured.
- Evidence: Globalping probes on five Armenian networks, TCP connect to AWS S3 endpoints: median 59 ms to Frankfurt (`eu-central-1`), 82 ms to Dublin (`eu-west-1`). Details in `docs/04-operations/costs.md`.
- Decision: Keep Supabase in `eu-central-1` and Vercel functions in `fra1`. The new `restaurant-os-dev` project is created there too.

## Phase 5 decisions

### ADR-035: Owner alerts go to Telegram, with web push as the fallback

- Status: Accepted, 2026-11-09
- Context: In 2021–22, 80 % of Armenian internet users used Viber, 62 % WhatsApp and 22 % Telegram (Caucasus Barometer, cited in `docs/05-business/positioning.md`). Many owners may not have Telegram.
- Decision: Keep Telegram for alerts and the day summary. Owners who don't use Telegram turn on web push notifications in the admin, which sends the same alerts to their phone's browser. On iPhones this works once the admin is added to the home screen.
- Rejected: a Viber bot (new bots cost €100 a month plus per-message fees, and need Viber's approval); WhatsApp Business messages (Meta charges per template message). Both break the free-only rule. SMS (paid per message).
- Consequences: The notification outbox gets a `web_push` channel next to `telegram`. The web push library goes through the Phase 2 dependency and license check before it's added. The human support chat can be in any messenger; it isn't a bot.

### ADR-036: Two plans, enforced in Postgres

- Status: Accepted, 2026-11-09. The owner delegated the Gate 5 decisions; prices are in `docs/05-business/pricing.md`
- Decision: `subscriptions.plan` is `menu` (free: QR menu, photo import, stop list) or `service` (paid: ordering, staff screens, Telegram, dashboard). Guest ordering functions and staff screens check the location's plan and status in Postgres; a location on `menu`, or `past_due` for more than 7 days, keeps its public menu and loses ordering. Every location starts with 30 days of `service` as a free month. Owners can export their menu, orders and bills as CSV from the admin at any time.
- Rejected: checking the plan only in the Next.js app (a direct RPC call would skip it); deleting data when a café stops paying.
- Consequences: Phase 6 migrations add `subscriptions.canceled_at`, `cancel_reason` and `converted_at`, rename the seed's `standard` plan, and add the plan check to `private.place_guest_order` and the staff RPCs. CSV export is a Stage 1 admin feature.

### ADR-037: Business metrics come from Postgres; PostHog only for the guest funnel

- Status: Accepted, 2026-11-09
- Decision: Add `kitchen_tickets.first_seen_at`, set when a kitchen screen reports that it has drawn the ticket, so order-to-kitchen time is measured in production. A `metrics_daily` table (one row per location per business day) is filled by `pg_cron` at 05:30 Yerevan time and read by platform admins through security-definer functions. PostHog tracks four guest events and nothing personal.
- Rejected: computing business metrics in PostHog (it would need order data and guest identifiers we don't want there); timing on the client clock (device clocks drift, R20).
- Consequences: Definitions and targets are in `docs/05-business/metrics.md`.

## Phase 6 decisions

### ADR-038: The app never holds the Supabase secret key

- Status: Accepted, 2026-11-09
- Context: The Phase 1 design gave the Next.js server the service-role key for guest orders, device pairing and background jobs. Two problems showed up when setting up the build. The tools this project is built with can read only a project's publishable keys, and secrets are never pasted into chat. And the service-role key is the one secret that bypasses every RLS policy (risk R14), so keeping it out of Vercel is safer anyway.
- Decision: Everything that needed the key moves into the database.
  1. Table QR tokens are signed and checked in Postgres (`private.sign_table_token`, `private.verify_table_token`) with HMAC-SHA256 keys stored in Supabase Vault as `qr_key_<kid>`. The keys are generated inside the database, so no person or tool ever sees them. The token format from ADR-006 doesn't change.
  2. Guests call `api.guest_join_table` and `api.guest_place_order` directly with their anonymous session. Each function checks the token, the session and the limits itself; the existing `private.*` functions stay as the internal core.
  3. A kitchen screen or waiter tablet signs in anonymously and redeems its pairing code with `api.redeem_device_pairing`. `private.is_real_user()` accepts an anonymous user only when it is an active device member, so guests still never match a staff policy. People join with `api.accept_invitation` after signing up.
  4. Background work runs in Postgres. pg_cron schedules it and pg_net calls the Telegram Bot API directly, with the bot token in Vault. Telegram's webhook goes to a small Next.js route that passes the update and its secret header to `api.telegram_update`, which checks the secret against Vault.
  5. Turnstile protects anonymous sign-in through Supabase Auth's own CAPTCHA setting instead of our server.
- Rejected: asking the owner to paste the key into chat (secrets never go through chat); injecting the key through the development network proxy (it would make test requests run as the service role and hide RLS bugs); Supabase Edge Functions for guest writes (a second runtime for no gain). Edge Functions stay the escape hatch for Auth admin tasks, since Supabase gives them the key automatically.
- Consequences:
  - Vercel holds only the publishable key and the AI provider key. `SUPABASE_SECRET_KEY`, `QR_SIGNING_KEYS`, `TELEGRAM_*`, `JOBS_SECRET` and `TURNSTILE_SECRET_KEY` leave the env list.
  - The plain-Postgres test harness stubs Vault and pg_net.
  - Some settings exist only in the Supabase dashboard, so the owner does them once: turn on anonymous sign-ins; turn off email confirmation for the pilot (the free email service only reaches the project's own team); raise the anonymous sign-in limit to about 300 an hour; later, add Turnstile and paste the Telegram bot token into Vault.
  - The cleanup job that deletes old anonymous users skips device members.

### ADR-039: The product is called Pativ (Պատիվ)

- Status: Accepted, 2026-11-09, chosen under the owner's delegation; easy to change
- Context: "Restaurant OS" was a placeholder. The pitch and the guest-facing app need a real name.
- Decision: Pativ, written «Պատիվ» in Armenian and «Патив» in Russian. «Պատիվ արեք» is what Armenians say when they set food in front of a guest, so the name is about hospitality without being a generic word like "menu" or "table". It's short, has no awkward meaning in Russian or English, and is easy to say in all three languages. Searches on 9 Nov 2026 found no Armenian business or app using it, and pativ.am was unregistered.
- Rejected: Seghan («Սեղան», table: too generic, and "gh" is hard for foreign guests); Tarkhun (a well-known soft drink brand); Tsiran (used by many businesses).
- Consequences: The UI reads the name from one message key (`brand.name`) and one constant, so a rename touches no logic. "Restaurant OS" stays as the internal project name in docs and code. Before spending money on the name (domain, printing, trademark), check the Armenian IP office register (aipa.am) and register pativ.am; both wait for the free-only rule to change.

### ADR-040: Telegram alerts are exceptions by default

- Status: Accepted, 2026-11-09
- Context: The video research (`docs/00-research/video-notes.md`, A4) heard owners say they want to be away from the café and hear only when something needs them. A busy café sends 70 orders in an evening; a message for each one teaches the owner to mute the bot and miss the late ticket.
- Decision: A new Telegram channel gets late tickets (`order.overdue`), a station screen offline (`station.offline`), a cancellation after serving (`order.comped`) and the day summary (`day.summary`). Every-order alerts (`order.placed`) are a switch in the Telegram settings, off by default.
- Rejected: every order by default (noise); no per-order option at all (some owners want it in the first week).
- Consequences: Migration `alerts_exceptions_default` changes the column default. The pitch, the onboarding test and the Friday walkthrough say so.

### ADR-041: Gemini model list for menu import

- Status: Accepted, 2026-11-09
- Context: Building the menu reader (Task 9.1) showed three things about the Gemini free tier. Each model allows 20 requests a day per project. Older models (gemini-2.5-flash) are closed to new users. And a response schema with length and count limits (`maxLength`, `maxItems`, `minimum`…) is refused with HTTP 400.
- Decision:
  - `GEMINI_MODELS` is a list, tried in order: `gemini-flash-latest`, `gemini-3-flash-preview`, `gemini-3.1-flash-lite`. When a model's daily quota is used up or the model is gone, the reader moves to the next one. One import (all pages of a menu) is one request.
  - The adapter calls the `v1beta` API, where structured output and the newest models are.
  - The schema sent to the provider keeps the structure only; Zod checks the limits on the reply.
  - Briefly overloaded servers (500/502/503/504) get two retries, after 2 and 6 seconds.
- Measured on the two sample menus in `tests/fixtures/menus/` (rendered, not photographed): `gemini-3-flash-preview` read every dish and price, left a price range empty, found the sizes of a drink and skipped the address and Wi-Fi line; about 1,600 input and 800–1,300 output tokens per page. `gemini-3.1-flash-lite` also passed, with plainer translations ("Pork barbecue" for խորոված).
- Rejected: one fixed model (an import fails for everyone after 20 a day); a paid tier (free-only rule).
- Consequences: About 60 imports a day across all cafés while the list holds, plenty for the pilot (imports happen once per café, then on menu changes). The real check is still 15–20 photographed Yerevan menus from the field visits (`gaps.md`). The free tier may use prompts to improve Google's products; the import screen says so.

### ADR-042: Kitchen board calls made while building milestone 6

- Status: Accepted, 2026-11-09 (sensible calls under the owner's delegation; easy to change)
- Decisions:
  1. **Server clock from our own route.** Ticket timers use `GET /api/time`, measured three times at load (shortest round trip wins) and again every 10 minutes, on reconnect and on wake (R20). Not an extra database function, so the board works on the schema as it is; Vercel and Postgres clocks are both NTP-synced, the tablet's is the one that drifts.
  2. **Timers show whole minutes, recomputed every second.** As in the mockup («հենց նոր», «8 ր»): a mm:ss age can be mistaken for the wall clock from 2 m, and the colours still flip on the exact second (8 and 12 minutes, constants until a setting exists).
  3. **What the board hides.** Ready food of a table that has already paid (waiters forget "served", R18, so the column would grow all evening); an order slip with nothing left to cook after cancellations (its red void slip tells the cook). A slip whose line was partly cancelled shows the new quantity with the old one struck through beside it.
  4. **The screen's language is `locations.kitchen_locale`** (i18n.md), for the chrome as well as the dish names. Names fall back hy → ru → en and carry `lang` when they differ.
  5. **No «Մատուցված է» on the kitchen board.** The mockup gives the Ready column «Վերադարձնել» only; serving is the waiter's tap (milestone 7).
  6. **Outbox conflicts drop the rest of that ticket's queue.** After a `stale_status` answer, later queued taps on the same ticket were made on a wrong picture, so they go too; one «Արդեն փոխվել է» per ticket, then a refetch. Kitchen-busy and stop-list changes are not queued: they need a connection and say so.
  7. **A disconnected device notices within one poll.** RLS makes a revoked device read nothing, which looks like a quiet kitchen; when the 10-second poll can no longer see its own location, the board shows «Այս սարքն անջատված է։». The heartbeat (60 s) and a refused tap say the same.
  8. **Stop list entries last the business day:** `until` is the next `business_day_starts` in the location's time zone.
  9. **The system's default station named "Kitchen" is shown as the localized «Խոհանոց»**; stations an owner named keep their name. Other stations of the location are links in the top bar, so a bar device paired to the default station can switch.
  10. **`api.set_kitchen_busy` also broadcasts a `location` event** on `loc:<id>`, so the other screens of the location update at once.

### ADR-043: Guest menu and ordering calls made while building milestones 4–5

  - **JavaScript budget.** The brief's "under 100 KB" for the guest menu can't be met on Next 16: the framework alone is about 148 KB. ### ADR-044: Telegram and web push calls made while building milestone 8

- Status: Accepted, 2026-11-09 (sensible calls under the owner's delegation; easy to change)
- Decisions:
  1. **Delivery runs in Postgres, every 10 seconds.** pg_cron runs `private.run_notifications()`: it reads pg_net's answers for rows in flight, then sends due rows. The order transaction only inserts outbox rows (ADR-016). A row in flight holds a 2-minute lease; no answer by then is a failure.
  2. **Retries at 1, 5 and 15 minutes, dead after 5 failures** (the plan's numbers; ADR-016 said 8 attempts). Telegram's 429 waits `retry_after`. "Bot was blocked" or "chat not found" turns the chat off and kills the row at once. Alerts that could not go out for 6 hours are dropped as `stale`, so a late token doesn't flood the owner with yesterday's orders.
  3. **No token, nothing happens.** Without `telegram_bot_token` in Vault rows wait as `pending` and nothing errors; the admin page says the bot isn't ready and offers phone notifications instead.
  4. **Bot replies ride on the webhook's answer.** `/start <code>`, `/stop` and wrong codes are answered by returning a Bot API method from `/api/telegram`, so linking needs no outgoing call and no token in the app. Link codes are 16 URL-safe characters, stored hashed, valid once for 30 minutes; a chat gets the language of the person who made the link. Removing the bot from a group or blocking it turns the chat off.
  5. **"During opening hours" without an opening-hours setting.** A kitchen screen is reported offline after 2 minutes without a heartbeat only while the café is serving: a table is open or an order came in during the last 45 minutes. One alert per outage.
  6. **"At closing time" for the day summary.** After 21:00 local time, once every table is closed and no order came in for an hour; if the café never got quiet, in the first three hours of the next business day. Days without orders send nothing. Test orders are left out.
  7. **Late tickets:** 20 minutes (a constant until the Settings screen has the field), one alert per order, tickets older than 3 hours are forgotten ones and not reported.
  8. **Web push without a library.** RFC 8291 encryption and RFC 8292 VAPID take about 100 lines on Node's crypto and are checked against the RFC 8291 test vector, so no dependency and no license review. The database can't encrypt, so pg_net posts `{id, attempt, sig}` to `/api/push`; the signature is an HMAC with `push_job_key` from Vault, valid for one attempt. The route trades it for the text and the devices (`api.push_claim`) and reports each push service's answer (`api.push_report`); 404/410 removes the device. The VAPID keys are Vercel env vars made by `scripts/gen-vapid.ts`, never printed.
  9. **Each person's phones are one `web_push` channel** with the same event switches and texts as Telegram; Telegram chats are shared by the café's owners and managers.
  10. **Configuration in Vault, not in tables:** `telegram_bot_token` (owner), `app_base_url` (where `/api/push` lives), optional `vercel_bypass_secret` (Vercel's "Protection Bypass for Automation", so pg_net and Telegram reach a protected preview). `telegram_webhook_secret` and `push_job_key` are generated inside the database.
- Rejected: an npm web-push library (a dependency for 100 lines of standard crypto); sending from a Next.js cron (needs a secret key or a job secret in the app, ADR-038); an opening-hours table now (one more setting before the pilot needs it).
- Consequences: Migrations `20261109200000_telegram_link`, `20261109200100_notification_delivery`, `20261109200200_web_push`. The harness stubs pg_net and pg_cron. The admin page is `/admin/telegram`.

### ADR-045: Sales dashboard, plans, export and platform admin calls made while building milestone 10

- Status: Accepted, 2026-11-09 (sensible calls under the owner's delegation; easy to change)
- Decisions:
  1. **The owner's dashboard reads one function, `api.sales_dashboard(location, from, to)`**, not `metrics_daily`. Today has to be live, and the numbers need joins across orders, items, tickets, bills and history that RLS-only reads would turn into a dozen round trips (and PostgREST's 1,000-row page). The function checks `owner`/`manager` at the location and caps a range at 93 days. `metrics_daily` stays the platform's history, filled by pg_cron (`pativ-metrics-daily`, 01:30 UTC = 05:30 Yerevan) as ADR-037 says; owners can also read their own rows through RLS.
  2. **What counts.** Money from paid bills only (void bills and open tables left out; open tables are a separate tile, screens.md 13). Orders, dishes, hours and sources from real orders (`accepted`, not `is_test`). Cancelled quantities come off a dish's count; reasons come from `order_status_history`.
  3. **Comparison: the same weekdays, shifted back by whole weeks** (7 days for a day or a week, 14 for 8–14 days…). When the range includes today, the comparison stops at the same time of day, so a lunchtime look isn't compared with a full evening.
  4. **"Weakest dishes" are the active menu dishes ordered least in the range, including those never ordered**, excluding the top five. A dish nobody orders is the most useful thing to show an owner.
  5. **No chart library.** The hour chart is about 100 lines of HTML and CSS in a server component: tarragon columns for the period, a grey level mark for the comparison, a legend, native tooltips and a table view. No client JavaScript and no dependency; Recharts would add a client bundle and a license review for one chart.
  6. **The dashboard isn't hidden on the Menu plan.** A Menu-plan café takes no orders, so it has no numbers; the plan banner says why. Plan state in the admin mirrors `private.location_can_order` (`src/features/billing/plan.ts`); Postgres still decides.
  7. **CSV export reads through the owner's own session and RLS**, filtered by the café as well, paged past 1,000 rows. It's a BOM-prefixed, CRLF, RFC 4180 file so Excel opens Armenian text, and text that a spreadsheet would run as a formula gets a leading apostrophe. Column names come from the messages; status and source values stay as their codes. One route per file: `/admin/export/{menu,orders,bills}`, linked from `/admin/export`.
  8. **The platform admin changes plans by hand** (Stage 1 bills by invoice): `api.platform_set_plan` sets the price (15,000 ֏, or keeps a founding café's existing price; 0 for Menu and the free month), `converted_at`, `canceled_at` and a month's `current_period_end`, and writes the audit log. "Devices online" means a heartbeat in the last 5 minutes; "offline devices" are active devices silent for over a day (opening hours come later, ADR-044).
  9. **Admin navigation is a layout around `/admin/**`**, from the mockup's sidebar; below 1024 px it is a scrolling row of tabs. `/admin/new` moved to an `(onboarding)` route group: a layout survives client navigation, so one drawn before the café existed would never show the sidebar after "Create".
- Consequences: Migration `20261109203000_dashboard_platform`. Its e2e tests skip until it is applied to the dev project (`E2E_M10_MIGRATION=applied`); the platform test also needs a platform admin account (`E2E_PLATFORM_EMAIL`, `E2E_PLATFORM_PASSWORD`).

### ADR-046: Waiter app calls made while building milestone 7

- Status: Accepted, 2026-11-10 (sensible calls under the owner's delegation; easy to change)
- Decisions:
  1. **Stale-table guard (ADR-033 (4), R8) as a separate "waiting" session.** A table "looks finished" when it has an accepted order, nothing waits for acceptance, every accepted order is served, and the guests asked for the bill or nobody ordered for 45 minutes. A new phone joining such a table gets a `table_sessions` row in the new `waiting` state instead of the old bill; the floor shows «Նոր պատվեր» and «Սեղան 6․ նոր հյուրե՞ր». Their orders never reach the kitchen by themselves: a `before update` trigger skips the automatic acceptance and `api.accept_order` answers `table_needs_closing`. The waiter either closes the old bill (`api.settle_table_session` then opens the waiting session; its orders still wait for «Ընդունել») or taps «Նույն հյուրերն են» (`api.seat_waiting_guests` moves the phones, orders and requests to the open bill). Phones that already belong to the old party keep it. This way `private.place_guest_order` (ADR-043) is not redefined.
  2. **One tap on «Գնում եմ» resolves the call** (`api.resolve_service_request`, idempotent). The guest can call again at once. Closing a table also resolves that table's open requests, so the next party doesn't start red.
  3. **Settling accepts cash and card only** (`card_terminal`), as the mockup offers; other methods are refused (`invalid_payments`) until Stage 3 brings online payment.
  4. **What is queued and what isn't.** Accept, reject, «Մատուցված է», «Գնում եմ» and the order pad go through the IndexedDB outbox (one per device user) and show at once with «Ուղարկվում է…» until a refresh confirms them. Settling, «Նույն հյուրերն են» and cancelling a line need a connection (realtime.md). A conflict shows «Արդեն փոխվել է» (or «Արդեն մատուցված է», «Նախ փակեք հին հաշիվը։») and refetches; after one, later taps on the same order or ticket are dropped (ADR-042, 6).
  5. **Floor layout.** Tables are drawn at `pos_x`/`pos_y` cells when every table of an area has them; otherwise (today: the tables editor has no positions yet) they flow in a grid by `sort`, then by label as a number. Round tables are circles, `rect` tables take two cells. Areas are tabs; tables without an area come last as «Այլ սեղաններ».
  6. **Live data.** Broadcast hints on `loc:<id>` trigger one refetch, debounced by 300 ms; a 15-second poll and a refetch on reconnect and on wake cover a dead socket (realtime.md). The location is the first one the member may see; a waiter device is paired to one.
  7. **The panel total is what the bill will be:** accepted orders only. Rejected rounds stay listed with their reason; a QR order that may be a duplicate (ADR-043) carries «Կարող է կրկնված լինել».
  8. **Reject and cancel reasons are short choices**, stored as text in the waiter's language (the guest page shows `reject_reason` as written). A waiter who opens «Չեղարկել» on served food sees that a manager must do it instead of a form; the database checks the same.
  9. **No sound on the waiter tablet yet.** The colour pulse and the counter carry new orders; sound and web push for waiters come with milestone 8's push channel if cafés ask.
- Consequences: Migration `20261109204500_waiter_app` (adds the enum value `waiting`, used only inside function bodies so it applies in one transaction). Its e2e tests (calls, the stale-table guard) skip until it and `20261109190300_guest_service_requests` are applied to the dev project.

### ADR-047: Calls made in the security review (Task 11.2)

- Status: Accepted, 2026-11-10 (sensible calls under the owner's delegation; details in `docs/06-build/security-review.md`)
- Decisions:
  1. **Web push only to the browsers' push services.** Endpoints must be https on `fcm.googleapis.com`, `android.googleapis.com`, `*.push.services.mozilla.com`, `*.push.apple.com` or `*.notify.windows.com`; the app, the server action and a table constraint all check it, and `/api/push` doesn't follow redirects. A new browser's push service means one line in each place. Rejected: resolving and blocking private IPs at send time (DNS rebinding makes that fragile, and nothing else is a legitimate endpoint).
  2. **A static CSP, with `'unsafe-inline'` for scripts and styles.** A nonce-based policy would make every page dynamic, including the statically rendered guest menu. The static policy still allows scripts only from our origin and network calls only to us and the Supabase project. Revisit if a third-party script is ever added.
  3. **`minimatch` advisory accepted rather than overridden.** The override planned in `dependency-audit.md` pulls in a package first published two weeks ago; the advisory is a denial of service through glob patterns only our ESLint config supplies.
  4. **Storage paths on rows are constrained in the table**, not only in RPCs, because owners and managers can update menu rows directly through RLS.
  5. **`members.pin_hash` is left out of the `select` grant**; Stage 2's PIN check goes in a SECURITY DEFINER function.
  6. **The SQL harness reproduces Supabase's default grants in `public`**, and `supabase/tests/sql/rls_coverage.sql` sweeps every public table from the catalog for each role, so a new table is covered without writing a test for it.
- Consequences: Migration `20261110100000_security_review` (constraints and a column grant; no new functions or tables), not yet applied to the dev project.

### ADR-048: Staff PWA, accessibility and overflow calls (Task 11.1)

- Status: Accepted, 2026-11-10 (sensible calls under the owner's delegation; easy to change)
- Decisions:
  1. **One manifest for the origin, started at `/pair?source=app`.** `app/manifest.ts` (Armenian name and description from `messages/hy.json`, PNG icons 192/512 plus a maskable one in `public/icons/`). The service worker turns that start URL into a 302 to the last staff screen it saw, online or offline; a device never paired gets the pairing page. Next.js links the manifest from every page, so a guest's browser may also offer to install; that is harmless and not worth a second manifest. The manifest can't follow each member's language, so it stays in the reference language.
  2. **What the service worker caches** (`public/sw.js`, extended, push handling unchanged): cache first for hashed `/_next/static` files and the icons; network first for the HTML of `/kitchen/<station>` and `/waiter` only, at most three screens plus a pointer to the last one. Never cached: other origins (Supabase REST and Realtime), `/api/*`, non-GET requests, RSC fetches, guest and admin pages. The cached staff HTML holds what the screen showed (tickets, table labels, guest notes), which is exactly what "opens offline at its last state" needs. A disconnected device is redirected by the server, and the worker then forgets that screen, so a revoked tablet doesn't reopen its old board offline.
  3. **Registration lives in an `(staff)` route-group layout** (`src/lib/offline/sw-register.tsx`). On the first visit the worker doesn't yet control the page, so the page posts the build files it loaded and the worker caches them and the screen; one online visit is enough. Works under ADR-047's CSP (`worker-src 'self'`, `manifest-src 'self'`; the worker only fetches our own origin).
  4. **No offline fallback page.** An uncached page offline shows the browser's own error; an offline page would need its own copy of the messages. Staff screens are the only ones that must open offline.
  5. **Accessible names come from what a control shows.** Waiter table buttons and order-pad dishes had `aria-label`s that didn't contain their visible text (axe `label-content-name-mismatch`, serious). They now build their names from their content with visually hidden words («Սեղան», «Ավելացնել՝») through rich messages (`waiter.tableName`, `waiter.pad.addItem`); a table reads «Սեղան 1 Ազատ»; the old `waiter.tableAria` and `waiter.pad.add` keys are gone.
  6. **Long table labels shrink.** A label longer than four characters (e.g. «Պատշգամբ 12», the database allows 12) is drawn at 36 px instead of 64 px on kitchen slips and at 20 px instead of 30 px on the floor map, and may break anywhere rather than spill out of the slip or button. Numbers keep the full size of the kitchen spec.
  7. **Overflow means more than page scroll.** `tests/e2e/overflow.spec.ts` also fails on text that runs out of its box or is cut off, and on boxes that scroll sideways without being meant to (tab rows say so with `overflow-x-auto`). That found the kitchen board's columns widening past a phone screen and clipping slips on a tablet, and the menu editor reserving the side panel's column while it was closed (dish rows crushed at 1280 px).
  8. **Every screen at every width.** The kitchen board and waiter app are designed for tablets, but they're also checked at 390 px: owners open them on phones. Checks run with the longest names the database allows (café name, dish names in three languages, a 12-character table label, a long kitchen note, a 9 990 000 ֏ price) on a fresh café per worker.
  9. **`@axe-core/playwright` 4.14.0 (MPL-2.0) as a dev dependency**, allowed for build and test tools by the license policy. axe runs with the WCAG 2.0–2.2 A/AA and best-practice tags; only serious and critical findings fail.
- Consequences: Screens that need migrations not yet applied to the dev project are skipped with the migration's name: `/admin/telegram` (`20261109200000_telegram_link`) and `/admin/dashboard` (`20261109203000_dashboard_platform`); the menu-import review page and `/platform`'s list need data those migrations create and aren't in the list yet. The menu editor's sold-out rows use the muted text colour instead of 50 % opacity (contrast 3.2:1 failed AA).

### ADR-049: Web push for guests and waiters (free, on the ADR-035 pipeline)

- Status: Accepted, 2026-11-10 (sensible calls under the owner's delegation; free only: browser push services, VAPID keys of our own, no paid service)
- Decisions:
  1. **Same pipeline, new audiences.** A web push is still an outbox row → `pg_net` → `/api/push` (signed per row) → RFC 8291 send. `notification_channels` gets an `audience` (`owner`, `waiter`, `guest`) and a `guest_session_id`. Waiter and guest channels have no alert events, so the owners' event queueing never reaches them; two small queueing functions feed them (`private.enqueue_guest_push`, `private.enqueue_waiter_push`). The owner's Telegram page lists only `owner` channels.
  2. **Guest: «Տեղեկացնել, երբ պատրաստ լինի».** A button on the order status page (shown while the latest order is received, accepted or cooking) asks permission, subscribes and calls `api.guest_push_subscribe(guest_session_id, subscription)`. The function checks that the caller owns an open guest session, accepts only the browsers' push services (ADR-047) and well-formed keys, caps the body at 2 000 bytes, allows 3 phones per guest session and 10 calls an hour. The database builds the notification: when an order's kitchen status becomes `ready` (a trigger on `orders`, only for guest orders), one row is queued for that guest session, deduplicated by order, so "ready, undo, ready" sends once. The text is rendered in the order's language: «Ձեր պատվերը պատրաստ է՝ սեղան 5» / «Ваш заказ готов — стол 5» / "Your order is ready — table 5". The path is the guest status page with the table's signed sticker, built in the database.
  3. **Guest devices are short-lived.** They are deleted when the table session closes or the guest session is revoked (triggers) and, as a backstop, after 24 hours or when the guest session has expired (`pativ-guest-push-cleanup`, every 15 minutes, pg_cron). Channels cascade to devices and queued rows.
  4. **Waiter: «Ծանուցումներ այս սարքում».** A switch in the waiter header calls `api.waiter_push_subscribe` (owner, manager or waiter, a paired tablet included; up to 5 devices per person). A new `service_requests` row, or a card/cash choice on an open bill request, queues a row for each subscribed active member who may see the location: «Սեղան 5․ կանչում են», «Սեղան 5․ հաշիվ», «Սեղան 5․ հաշիվ՝ քարտով». Resolving a request and repeat taps push nothing. In the spirit of ADR-040 only calls and bills push, never every order.
  5. **Notification behaviour.** Tags are per order (`order:<id>`) and per table and kind (`table:<id>:service.call`), so a repeat replaces the earlier notification and, with `renotify`, buzzes again. A tap opens the guest status page or `/waiter`; an open window of that page is focused (or navigated when the link differs). The service worker accepts only paths on its own origin. `push_claim` decides tag, link and `renotify` per event; owner alerts are unchanged.
  6. **Live notifications go stale in 15 minutes**, not 6 hours: a call from last night is noise.
  7. **No sound or app badge** beyond what the browser's notification does. Texts live in the database (`private.render_notification`), as for Telegram; the page's button and the waiter switch use `messages/*.json`.
- Limits:
  - **iPhone.** Safari delivers web push only to a page added to the home screen (iOS 16.4+). The guest button then gives way to a short note and the live status page keeps working; the waiter switch says the same. A waiter tablet installed from the home screen works.
  - One browser has one subscription per origin: the same browser used as a guest, then as a waiter or owner, moves its single subscription (the endpoint is unique). Not a problem on separate devices.
  - Push services may delay or drop a message; the status page and the waiters' floor map stay the source of truth.
- Consequences: Migration `20261110130000_push_guests_waiters` (not yet applied to the dev project; CI applies it on push). Its e2e test skips until then. VAPID keys must be set in the environment (`scripts/gen-vapid.ts`); without them the guest button is hidden and the waiter switch is absent, and nothing else changes.

### ADR-050: Pilot readiness: nightly backup and automatic test-data clean-up

- Status: Accepted, 2026-11-10 (sensible calls under the owner's delegation; free only: GitHub Actions and `pg_cron`)
- Decisions:
  1. **One cloud project hosts CI test cafés, the demo and the pilot café**, so a daily job (`pativ-purge-test-data`, 02:40 UTC) calls `private.purge_test_cafes()` and `private.purge_demo_activity()`. A café is a test café only if it has an owner, is older than a day, is not `demo-cafe`, and every person member has an `@pativ.test` email (the address all e2e helpers sign up with). One real member keeps it. Test users with no café are deleted afterwards, never platform admins. Anonymous users are left alone.
  2. **Demo café keeps its menu, tables and stations**; only its orders, bills, table and guest sessions and service requests older than a day are deleted.

  2. **Menu engineering (Kasavana and Smith), per section.** `api.menu_engineering(location, from, to)` (owner or manager, at most 93 days, accepted non-test orders): a dish is popular when its units sold reach 70 % of its section's average; it is profitable when its margin per unit reaches the section's sales-weighted average. The margin is price − cost only when every dish of the section has a cost (basis `margin`), otherwise the price (basis `price`), and the page says so with a link to add costs. Managers always get basis `price`. Quadrants are named in plain words, with one action each (keep and show first; try a small price rise; add a photo or feature; consider removing), never as stars, plowhorses, puzzles and dogs.
  3. **Busy hours.** `api.sales_heatmap(location, weeks)` returns average accepted orders per local ISO weekday and hour over the last 1–26 complete weeks. The page draws a 7 × open-hours HTML table in five ink strengths (no chart library, no colour legend needed), with the busiest and the quietest open hour as sentences and every cell's value in its text for screen readers.
  4. **Where it lives.** `/admin/dashboard/menu` (30 or 90 days, ending yesterday), linked from the sales page.
  5. **Admin home shows the café, not the sidebar again.** Today's revenue (with the change against the same time last week), orders and open tables from `api.sales_dashboard`, and a short to-do list built from RLS counts: menu never published or changed since publishing, no tables, no paired device, dishes without a photo, dishes sold out today. Each row links to the page where it is fixed. The eight shortcut cards with green icon tiles are gone; navigation stays in the sidebar and the phone pill row.
- Consequences: one migration with plain-Postgres tests (`supabase/tests/sql/menu_insights.sql`). Until CI applies it, the analysis page shows its error notice and the editor hides nothing (costs load empty); dish saves never call `set_item_cost` unless the cost was changed.

### ADR-059: Waiting-room games stay on plain canvas 2D, scale their resolution to the phone, and take the café's tokens

### ADR-062: Kitchen board arena pass: allergy banner, all-day counts, item-level bump, per-screen sound, visible edges

- Status: Accepted, 2026-11-19 (arena lane "kitchen"; sensible calls under the Gate 5 delegation; free only, no new dependency, no migration). Numbered 062, not 057: every arena lane started from ADR-056 and took 057, so the lanes are numbered in alphabetical order (admin 057, brand 058, games 059, guest-a 060, kitchen 062, waiter 063) to merge without a clash.
- Decisions:
  1. **Allergy notes are loud.** `mentionsAllergy()` in `board-model.ts` matches allergy and intolerance stems in Armenian, Russian and English at the start of a word (`ալերգ`, `անհանդուրժ`, `аллерг`, `непереносим`, `allerg`, `intoleran`, gluten, lactose, coeliac and so on; "minute" does not match). Nuts are also an ordinary wish («ընկույզով», "extra nuts"), so a nut word (`ընկույզ`, `գետնանուշ`, `орех`, `арахис`, nut, peanut, walnut, hazelnut) counts only right after a "without / no" word, with at most two words between and no comma («առանց ընկույզի», «без грецких орехов», "no peanuts"), or before "-free" ("nut-free"); "extra nuts", «Побольше орехов», "nutmeg" and "donut" stay ordinary notes. A missed allergy costs more than a false alarm, so explicit allergy and intolerance words always count. A ticket whose order note or a still-wanted line note matches gets a red banner under its head band (`ShieldAlert` + «Ալերգիա․ կարդացեք նշումը»), and the note itself is red-edged with a shield instead of the amber speech chip. A plain wish ("no onion") stays an ordinary note. The guest's allergen filter is not sent with the order yet: that needs a `place_order` change and a migration, so it waits; the keyword match covers what guests and waiters type today.
  2. **Sounds per event and per screen**, generated with WebAudio oscillators (no audio files): new order two short beeps, cancellation a falling pair, allergy order a fast four-beep alarm. One sound per refresh, the most urgent one. Each screen picks a pitch (high, middle, low) on the start-shift overlay, stored in `localStorage` per station, so two tablets side by side are told apart by ear.
  3. **All day.** A strip under the header (`all-day.tsx`) totals each dish across order tickets in New and Cooking, biggest batch first, with option variants listed under the dish. Tapping a dish outlines the tickets that contain it. The strip folds away; each screen remembers that in `localStorage`. Pure client derivation (`allDay()`), unit-tested.
  4. **Item-level bump, local only.** In Cooking each line is a 56 px button; tapping it strikes the line and turns its quantity box green. When every wanted line is struck, the ticket moves to Ready through the existing `set_ticket_status` action (outbox, compare-and-set). Strikes live in `sessionStorage` on that one screen and are pruned when the ticket leaves Cooking; two screens on the same station do not share them (the ticket status itself is shared as before). Persisting per-line state for the waiter (a column, a `SECURITY DEFINER` function, an outbox kind and an SQL test) waits until a pilot café asks for it.
  5. **Colours on the light board** (re-measured against ADR-056): the board has one red, `#b0213a` (white on it 6.7:1), for the late band, the allergy banner and the cancellation button; the hurry border is `apricot-deep` `#c9780f` (3.0:1 on white); the on-time band is `#dde0e6` and an on-time ticket has a `#c4c9d1` frame, so it is visible at 1.5 m; white header controls get a 2 px `staff-field` inner edge (3.4:1) instead of floating unseen on the near-white bar (1.07:1); the dark-era hover brightening no longer applies inside `.kitchen-light`. The note chip uses a token (`--kds-note`), with an icon so colour is never alone. «Շտապել» became «Շտապ»; the kiosk source is «Տերմինալ» / «Терминал» / "Terminal" on the board (the waiter's key is the waiter lane's).
  6. **Timers past 99 minutes show hours** («38 ժ»), so a forgotten ticket does not print «2290 ր».
- Consequences: UI only; no schema, RLS, function, route or realtime change. The kitchen e2e checks the hurry border as `rgb(201, 120, 15)` and the late border as `rgb(176, 33, 58)`, and has a new test for the allergy banner and sound, the all-day counts and the item-level bump.

### ADR-063: Waiter app keeps in touch with the table: timeline, quiet cue, quick actions, a visible outbox and «Իմ հերթափոխը»

- Status: Accepted, 2026-11-19 (scout findings for the waiter lane; sensible calls under the Gate 5 delegation; free only, no new dependency, no migration). Numbered by lane in alphabetical order at the arena merge (ADR-062 explains).
- Decisions:
  1. **Table timeline.** The panel lists the table's moments oldest first («Ինչ է եղել»): guests sat down, each round, a staff accept, food ready and served per station, an open call, an open bill request. The floor read adds `orders.accepted_at, accepted_by` and `kitchen_tickets.ready_at, served_at` (columns from the baseline; RLS unchanged). An accept is a moment only when a staff member accepted a guest's order (`accepted_by` set, source not `waiter`); auto-accepts and a waiter's own orders are one moment. Answered calls are not fetched, so they are not on the list rather than invented.
  2. **Ages on the map.** A tile shows how long its most urgent thing has waited (ready counts from `ready_at`, not from the order). A seated table with no new moment for 20 minutes (`QUIET_MINUTES`) shows «լուռ է …» in amber text and the panel says it is worth a look: with QR ordering the risk is that nobody walks over. Times from 60 minutes read as hours and minutes.

Each only when it can't be the wrong thing (`quickAction()` in `floor-model.ts`, unit-tested): no quick accept for a possible repeat, two new rounds or a party waiting for the old bill; no quick close while an order waits. The row itself still opens the table.

Tiles with a waiting tap get an amber dot. Settling and cancelling stay online-only (realtime.md).

It counts bills by `bills.closed_by` (the member; `payments.recorded_by` holds the auth user id, so it is not used). Only the caller's own numbers, no comparison with colleagues (metrics.md: no leaderboards).
  6. **Colours after ADR-056.** Free tables are an empty dashed outline (`line-strong`, 3.1:1 on the grey); seated tables a white card with a full tarragon edge (5.6:1 on the grey, it was 1.9:1); new orders the amber fill with an `amber-text` edge; selected choices in the reject, cancel and settle sheets are black, not green. Green stays for ready, served and "everyone is looked after".
  7. **Deferred:** moving a party to another table and handing a table to a colleague need a `SECURITY DEFINER` function, an SQL test and guest-side handling of the moved session; they are not in this change.
- Consequences: UI and reads only; no schema, RLS or function change. `Outbox` gains `discard()`, the provider `retry()` and `discard()`. The waiter e2e covers the timeline, the shift sheet, a quick «Գնում եմ» and the outbox sheet.

### ADR-064: One lock order for an order's rows, and one owner sign-up per e2e run

- Status: Accepted, 2026-11-19 (platform, round 2; sensible calls under the Gate 5 delegation; free only, no new dependency).
- Context:
  1. `api.set_ticket_status` (kitchen moves a ticket) locked the ticket, and its status update then updated the order row through the `kitchen_tickets_sync_order` trigger: ticket, then order. `api.cancel_order_item` (waiter cancels a line) locked the line, then the order, then wrote the ticket: line, order, ticket. Run at the same moment on one order, each held what the other wanted and Postgres ended one with 40P01.
  2. A full browser run signed up a new owner for every café it needed: at least 51 sign-ups without the demo owner's password (as in CI) and about 78 with it, all from one address within minutes. Supabase Auth limits sign-ups and sign-ins per address (30 per 5 minutes by default), and the form's "sign up, /admin/new, create café" path was where runs failed.
- Decisions:
  1. **Lock order: order, then kitchen ticket, then order line.** Migration `20261119120000_ticket_lock_order` re-creates both functions. Each finds the order with a plain read (a ticket and a line never change their order), takes `orders … for update` first, then the ticket, then the line, and only then reads what it decides on. Checks, their sequence, error codes, `security definer`, `search_path = ''` and grants are unchanged. `api.accept_order` and `api.reject_order` already lock the order first. New functions that write an order's tickets or lines take the locks in this order.
  2. **Two stale reads close with it.** `cancel_order_item` chose between "cancel the ticket" and "send a void ticket" from a ticket status read without a lock; and two stations finishing at the same moment could each compute the order's kitchen status without seeing the other's ticket. Both are now serialised on the order row.
  3. **The SQL test proves the order with a second session.** `supabase/tests/sql/ticket_lock_order.sql` holds a row lock in one session and calls the function from another over `dblink` (contrib, in the `postgres:16` image CI uses; local socket, test database only). While the call waits, rows later in the order must be free (`for update nowait` succeeds) and rows earlier must be held. Then 16 simultaneous moves and cancellations must all succeed. Against the baseline functions the first check fails.
  4. **One owner for the whole e2e run.** `tests/e2e/global-setup.ts` signs up one owner; each worker signs in as that owner once (`run-owner.ts`) and gets the session both as a Supabase client and as the app's own cookies (written by `@supabase/ssr`, the client the server uses). Every test still creates its own new café (`createFreshCafe`, `createCafeWithMenu`) through `api.create_restaurant`; the browser is pointed at it with the `pativ-restaurant` cookie that `requireMember` already reads. No assertion was removed or loosened, and tests that need an empty menu or no tables still get them.
  5. **The sign-up form keeps one test per screen size.** `onboarding.spec.ts` "a new owner signs up, creates a café" is the only form sign-up. It waits up to 30 s for each step and, when the form shows the refusal, fills it in again once after 65 s. The "taken page address" test opens `/admin/new` as the run's owner. API sign-ups and sign-ins retry once after a 429 the same way.
  6. **Because one owner now owns many cafés,** test queries through the owner's session name their café (device members, kitchen tickets), and the owner's second screen in the kitchen test is opened with cookies instead of the sign-in form.
- Consequences:
  - Sign-ups per full run: 4 without the demo owner's password (1 in global setup + the onboarding test on phone, tablet and desktop), down from at least 51 (27 through the form in menu, import, tables, Telegram and dashboard tests, 6 in onboarding, 18 for guest cafés). With the password: at least 13, down from about 78: the same 4, plus the invited manager in `staff.spec.ts` (3) and a café-less newcomer per worker in the a11y and overflow worlds (6); these test sign-up or need a person without a café. Counts are for one worker per screen size; each extra or restarted worker used to add sign-ups and now adds one sign-in.
  - Not changed, and a possible next limit: every guest who orders or calls a waiter is an anonymous Auth user (`signInAnonymously`), which Supabase limits per address too (30 an hour by default). A full run from one address makes several dozen.
  - A moved ticket and a cancelled line of the same order now wait for each other for the length of one short transaction instead of one of them failing. Staff clients need no change.
  - The migration reaches `restaurant-os-dev` through the CI `migrate` job after the push. Until then the cloud database still has the old functions, so the browser tests cannot show the fix; the SQL test does.
  - A worker's session lasts one hour (the Auth default). A single worker process that runs longer than that would need a new sign-in; no run comes close today (CI stops at 20 minutes).
  - The run's owner sees every café of the run through RLS, so a test that forgets to name its café could touch another test's rows. `TestCafe` no longer carries an email and password, which makes signing in "as this café's owner" a compile error.

### ADR-065: A second wordmark for dark backgrounds, Mrs Saint Delafield, and the effects are our own code

- Status: Accepted, 2026-11-19 (brand, round 2; sensible calls under the Gate 5 delegation; free only, no new dependency).
- Context:
  1. A café had one wordmark picture. Blanca's is drawn in dark ink, and its header band is dark brown, so the name was hard to read at the top of the menu. The slim bar that stays while the menu scrolls showed the café's name as text, cut off when it was long, even when the café had a wordmark.
  2. The owner asked for the script font Mrs Saint Delafield.
  3. ADR-052 allowed only code under permissive licences. Four effect files said "after React Bits (MIT + Commons Clause)", and StarBorder said "adapted from". Commons Clause is not on our licence list, so each file had to be either provably our own or gone.
- Decisions:
  1. **Two wordmark slots.** `restaurants.brand` keeps `wordmark` (artwork for light backgrounds, so everything saved before still works) and gains `wordmark_dark` (light artwork for dark backgrounds). Migration `20261119203419_brand_wordmark_dark` adds the key to `private.brand_shape_ok` and a second table constraint, `restaurants_brand_wordmark_dark_scoped`, that keeps the path in the café's own folder. `api.set_brand` and `api.public_menu` pass the object through and are unchanged.
  2. **The page picks by what is behind the picture.** `pickWordmark(brand, background)` in `brand.ts` takes the dark-background picture when white reads better than black on that colour (WCAG contrast, the same test the brand tokens use), else the light-background one, and falls back to the only picture there is. The header band's background is the brand's header colour, or the page when there is none; the slim bar's is the page (the brand's page colour if the theme accepts it, else the theme's). The server works this out (`wordmarkTones`) and hands the guest's client code two paths, so `brand.ts` stays out of the guest bundle.
  3. **The slim bar shows the wordmark** (40 px high, the café's name as its `alt`) when the café has one, and the name as text otherwise.
  4. **The editor has both slots side by side,** each previewed on the kind of background it is for: the café's own page or header colour when that is light (dark), else a plain light (dark) chip. The preview uses the same pick as the guest page.
  5. **Before the migration reaches a database,** reads work as before: a brand without `wordmark_dark` parses to "no dark wordmark" and the one picture is used everywhere. Saving a brand that has a dark wordmark or the new font is refused by the old `brand_shape_ok` and the editor shows its usual "could not save"; nothing is half-saved.
  6. **Mrs Saint Delafield** joins the script fonts (28 families now) in `BRAND_FONTS` and `private.brand_fonts()`. It is SIL OFL 1.1 and, unlike the rest of the list, Latin only (checked against the css2 API on 2026-11-19: `latin`, `latin-ext`, weight 400). Russian and Armenian section titles fall back per glyph to the serif stack, as Armenian already does for every script font; the editor says so under the script field. `brand.test.ts` now compares the list with the newest migration that defines `private.brand_fonts()`. Loading is unchanged: one css2 stylesheet added after first paint; `fonts.googleapis.com` and `fonts.gstatic.com` were already in the CSP.
  7. **Unused effect files are deleted:** `star-border.tsx`, `star-border.module.css`, `themed-star-border.tsx` (the one file marked "adapted from React Bits") and `motion/rotating-text.tsx` with its CSS. Nothing imported them since ADR-061. The `--guest-star` tokens stay: the tap spark and the ready-order ring light use them.
  8. **The three effects in use are our own implementations.** `motion/tilt.ts`, `motion/split-text.tsx` and `motion/spark.ts` (with `burst.ts`) were read side by side with the React Bits sources of the same names (repository `DavidHDev/react-bits`, `src/ts-default`, as published on 2026-11-19). They share the idea and nothing else. Upstream Tilted Card is a React component with its own spring integrator in a frame loop, a flip side, a caption and `--tc-*` variables; ours is a hook that calls Motion's `animate()` with a spring and sets `data-tilt` and `--glare-x/y`. Upstream Split Text uses GSAP's SplitText and ScrollTrigger; ours splits by grapheme with `Intl.Segmenter`, plays in CSS at load and with an `IntersectionObserver` and Motion below the fold. Upstream Click Spark draws on a canvas; ours animates a dozen spans with Motion. Two default numbers coincide in the tilt (12 degrees, 800 px perspective); numbers of that kind are not code. So no code was rewritten: the file headers now say what the files are (our implementation of a common idea the owner picked from that gallery, no code copied) instead of "after React Bits (MIT + Commons Clause)".
- Consequences:
  - Blanca needs its cream wordmark uploaded in the second slot by the owner (or a tester through the editor) once the migration is applied; no data was changed by hand.
  - A café that uploads only a dark-background picture gets it on light backgrounds too, where it may be hard to read; the editor's two chips show this before saving.
  - The comparison in 8 was made against today's upstream. If React Bits published a different version on 17 Nov 2026 (when ours was written), that version was not read; our files' structure (Motion mini, CSS keyframes, spans) follows from ADR-052's own engine choice, which upstream has never used.
  - The slim bar loads one more small picture when the two bars need different wordmarks.

### ADR-066: Owner sets allergens in the dish editor, dates read dd.mm.yyyy, and old test orders can be left out of the dashboard

- Status: Accepted, 2026-11-20 (owner admin, round 2; sensible calls under the Gate 5 delegation; free only, no new dependency).
- Context:
  1. Guests see allergens and use an "I avoid…" filter, but `api.save_item` did not take `allergens`, so only seed data had any. It also took any tag text, and the guest menu shows seven tags while the editor offered four.
  2. A demo café's dashboard counted its old test orders. Every dashboard, metrics, insights and export query already leaves out `orders.is_test`, but nothing could set it.
  3. A native date input shows the browser's order, not the dd.mm.yyyy that Armenian and Russian readers expect. The other admin dates already go through `formatDate`.
- Decisions:
  1. **`save_item` takes `allergens`** (migration `20261120090000_dish_allergens`, same signature, grants unchanged). A missing key keeps the stored list, so an older client or an import doesn't wipe it; an empty list clears it. Allergens must be among the 14 EU values and tags among the seven the guest menu knows (`invalid_allergen`, `invalid_tag`). The editor gets a second row of toggle buttons for allergens (labels reused from `guest.allergens`) and the three missing diet tags (vegetarian, gluten-free, lactose-free). An empty list still means "not filled in", never "free of allergens" (the guest menu already says so).
  2. **Test data is a flag on a range of days, not a start date.** `api.set_orders_test(location, from, to, is_test)` (owner or manager, audit-logged, up to 366 days, migration `20261120090100_orders_test_flag`) flips `is_test` for the orders of those business days. A start date would have needed a new setting read by five functions; the flag reuses the `not is_test` rule they already have, also fixes the export and metrics, and can be undone. The dashboard has a collapsed "Test orders" panel under the numbers, with a confirm step, acting on the range being shown.
  3. **Dates:** on the dashboard range form, hy and ru get a text field that shows and reads dd.mm.yyyy (`parseDateInput` also accepts `/`, `-`, short days and ISO, so the plain GET form still works without JS); en keeps the native date picker. The server turns the text into ISO before `resolveRange`.
- Consequences:
  - Existing dishes have no allergens until the owner fills them in; the guest filter keeps marking them "ask the waiter".
  - Flagging is by business day, so a café that wants to keep today's real orders must leave today out of the range.
  - Amendment (migration `20261120100000_bills_test_orders`): paid bills were still summed with no test filter, so flagged orders kept their revenue and average check. A paid bill is test data when its table session has at least one order and every order of that session is `is_test`; bills with no session, or with one real order, still count.
  - Fixed in `api.sales_dashboard` (paid, prev_paid), `private.compute_metrics_daily` and `private.day_summary_payload`; the bills CSV export stays a raw ledger (the orders export carries the test column).
  - The one-off flagging of Blanca's and the demo café's old orders is left to their owners, through the panel; no data was changed by hand.

### ADR-067: Ready-made staff logins (username and password) for the waiter and the kitchen

- Status: Accepted, 2026-11-20 (owner decision: café owners are too busy to set up staff devices; sensible calls under the Gate 5 delegation; free only, no new dependency, no Supabase Auth setting changed).
- Context:
  1. A kitchen screen or waiter tablet was connected with a six-digit code the owner makes in /admin/staff, and waiters as people joined by invite link. The owner wants every café to have a working waiter login and kitchen login that Pativ hands over, which the owner may change but never has to.
  2. ADR-038: the app never holds the Supabase secret key, so it cannot call the Auth admin API. Business rules stay in Postgres.
  3. `private.purge_test_cafes()` deletes users with an `@pativ.test` address and cafés whose people all have one.
- Decisions:
  1. **A staff login is an ordinary person.** An auth user, a `members` row (`kind = 'person'`, role `waiter` or `kitchen`, one location) and a row in `public.staff_logins` (username, kitchen station, whether a password was set). Every waiter and kitchen function and every RLS policy already goes through `private.my_location_ids`, so nothing in them changed; a login has no admin role, so no admin page or function opens for it. Pairing codes and invitations stay as they are.
  2. **Usernames.** `<café slug>-<ending>`: lowercase letters, digits and hyphens, 3 to 64 characters, unique across the platform (`staff_logins.username`). The owner may type the ending (1 to 15 characters); by default it is `waiter`, `kitchen`, then `waiter-2`, `kitchen-2` and so on. The slug prefix keeps one café from taking another's names. Slugs and endings can both contain hyphens, so two cafés could ask for the same name by different routes; the second one gets `username_taken` (or the next number for the automatic ones).
  3. **The reserved address is `<username>@staff.pativ.invalid`.** `.invalid` is reserved (RFC 2606): it can never be delivered to, so no real person owns it. It does not end in `@pativ.test`, so the nightly purge never matches it. The dev project's Auth accepts it at sign-in (checked: a wrong password for such an address answers `invalid_credentials`, not an address error). The domain is in `private.staff_email_domain()` and `src/lib/auth/staff-login.ts`.
  4. **Creating the auth user inside a definer function, not by a server-side sign-up.** `api.create_staff_login` (owner or manager of the location, `SECURITY DEFINER`, `search_path = ''`) inserts the `auth.users` and `auth.identities` rows exactly as `supabase/seed.sql` does, with a bcrypt hash made by pgcrypto, and the member rows, in one transaction. The alternative was a server action that signs the user up with a second non-persisting client and then attaches the membership. It was rejected because it depends on Auth settings we do not control from the repo (sign-ups on, e-mail confirmation off, CAPTCHA, address validation, per-IP sign-up limits that the e2e run already hits), because anyone could register `<name>@staff.pativ.invalid` first and take the name, and because user and membership would not be created atomically. The price is that we write rows in `auth` ourselves; the seed and `api.revoke_member` already do, and the SQL tests run the same statements. A user somebody registered on their own is never adopted: the name counts as taken.
  5. **Set a new password.** `api.set_staff_password` checks that the caller is owner or manager of the login's café and that the target is one of its staff logins, sets the bcrypt hash, and ends the login's sessions and refresh tokens. A staff login changes its own password on the waiter and kitchen screens (a key button in the top bar) with `supabase.auth.updateUser`.
  6. **Passwords.** Made in the server action with Node's CSPRNG (`randomInt`, no modulo bias): 10 characters from an alphabet without `0 O 1 l I` (about 57 bits). The owner may type one instead (8 to 72 bytes). The password is shown once in the page, sent to the database over TLS and kept only as a bcrypt hash; it is never logged or stored in clear. Sign-in limits are Supabase Auth's own; we added none.
  7. **Switch off and on.** `api.set_staff_login_active` sets `members.is_active` (every waiter and kitchen function refuses at once), bans the auth user (`banned_until` 100 years ahead: no new sign-in) and ends its sessions. Switching on lifts both. This is enforced in the database, not the UI.
  8. **Sign-in.** On /login a value without `@` is a username and becomes `<username>@staff.pativ.invalid`; an e-mail is used as typed. After signing in, `api.my_staff_login()` sends a waiter login to /waiter and a kitchen login to /kitchen/<its station> (the default station unless the owner chose one). Everyone else goes where they went before.
  9. **Ready-made.** `api.create_restaurant` creates `<slug>-waiter` and `<slug>-kitchen` with every new café (the kitchen one on the default station). Nobody knows their passwords: the database makes a random one and discards it. The owner opens "Staff logins", presses "Set a new password" and the generated password is shown once, ready to write on the wall or hand over; until then the row says "Password not set yet". This was chosen over "generate on first visit and show once" because that needs the clear text stored until first visit. Existing cafés get nothing automatically: the owner (or we, with the owner) presses "Add a login". Staff logins cannot call `api.create_restaurant`.
  10. **The purge.** A café is judged by its people, so staff logins are left out of the "every person is @pativ.test" check: a test café with its two logins is still purged, a café with a real owner is never touched. After the cafés are deleted, staff-login users that no longer have any member are deleted too; a login of a café that still exists has a member and is never matched.
  11. **The owner screen.** /admin/staff gets a "Staff logins" section above people and devices: username, role, station when it has a name, status, "password not set yet", last sign-in (from `auth.users`), "Set a new password", "Switch off / on", and "Add a login". Staff logins are not listed again under People.
- Threat model:
  - Several people share one login on a shared device, so there is no per-person trail for a login, only for the café. The audit log records create, password and switch events with the actor. Someone who needs a person trail should use an invitation.
  - A leaked staff password opens one café's waiter or kitchen screen: orders, tickets, tables and the menu as published. It cannot open any admin page or call any admin function, read another café (RLS), start a café, create logins or reset any password. The owner's answer is "Set a new password" (sessions end at once) or "Switch off" (also bans sign-in).
  - Guessing is limited by Supabase Auth's own sign-in limits. A password has about 57 bits when we make it. A short typed password (8 characters) is allowed because the owner asked to choose their own.
  - A staff login can change the address on its own auth user (`updateUser`). That only breaks sign-in by username for that login; it gains no rights, since authorisation is the member row, not the address. A new password does not bring the address back; the owner then replaces that login.
  - There is no password reset by e-mail for a staff login: the address cannot receive mail. The owner resets it.
  - Passwords pass through the Next.js server for a moment on creation and reset (they are made or typed there). They are not logged by the app; a platform that logs request bodies of server actions would capture them, so none should be enabled.
  - Switched-off logins keep their rows and name, so the name cannot be taken by another café.
- Consequences:
  - Every new café now has two more auth users and members. `api.list_staff_logins`, the member counts in the tests and the harness stubs (`auth.users` columns, `auth.identities`) were updated for that.
  - Before the migration reaches a database, /admin/staff leaves the section out and the sign-in form works as before for e-mail addresses.
  - A "We do it for you" add-on is proposed in `docs/05-business/pricing.md`, not decided.
  - If Supabase changes the `auth.users` columns, `private.make_staff_login` and `supabase/seed.sql` must change together.

## ADR-068: Availability controls (category hours, pause, closed kitchen) and the guest menu's refresh

- Status: Accepted, 2026-11-23 (owner spec, Phase 1.1; free only, no new dependency).
- Context: owners need to stop or limit ordering without calling us, and a guest's open menu must not go stale: sold-out dishes, a pause or a closed kitchen must show within seconds. Guests must never meet a broken experience (an order that fails for a reason the menu did not show).
- Decisions:
  1. **Category hours.** `categories.available_from/available_to` (time, both or neither, not equal; may span midnight), read in the café's `locations.timezone`. They are read live, not from the published snapshot, so a change needs no Publish. Outside its hours a section is hidden from the guest menu (`hidden_categories` in `api.public_menu`), not greyed. `place_guest_order` refuses any dish of a hidden section with `category_unavailable` (the page reloads the menu). Set with `api.set_category_window`.
  2. **Pause.** `locations.ordering_paused` + `ordering_paused_until`. Paused means the flag is set and the end is null or in the future, so a timed pause ends by itself with no job. `api.set_ordering_pause(location, paused, minutes default null)`: 1 to 720 minutes, or until resumed. `qr_ordering_enabled` (the hard off and its `ordering_disabled` message) is unchanged.
  3. **Close kitchen for today.** `locations.kitchen_closed_until` = the next `business_day_starts` in the café's zone, the same boundary as the stop list's "not today". `api.set_kitchen_closed_today(location, closed)`. The kitchen-busy timer (`kitchen_busy_until`) is a separate thing and unchanged. We did not use `location_hours`: they are not enforced anywhere else.
  4. **Where it is enforced.** `private.place_guest_order`, before the rate limit and only when the order is new (a retry of an order already placed still returns it). Errors `ordering_paused`, `kitchen_closed`, `category_unavailable`. Waiters place orders through their own function and are not held back. Joining a table and reading the menu stay open while paused, so guests see why.
  5. **Who.** The three setters are `SECURITY DEFINER`, `search_path = ''`, check `private.assert_location_role(..., '{owner,manager}')` (the category one the restaurant role), write `audit_log`, are not executable by anon or public. The new columns have no client write grant, so only these functions change them. The Telegram bot can call them as they are.
  6. **Section on/off.** `api.save_category` gained `p_is_active` (null keeps the stored value). An off section and its dishes leave the next published menu, so guests see it after Publish (the editor says so).
  7. **Refresh: visibility-aware polling of one tiny RPC.** The open menu calls `api.public_menu_status(location_id)` every 10 s while the tab is visible (version, hard off, pause, closed, stop list, hidden sections, busy timer; about 300 bytes). It compares the answer with what the page shows and calls `router.refresh()` only when they differ, so the full menu is fetched only on a change. A hidden tab stops polling and polls once on return; errors back off to one minute and show nothing. The call is a plain `fetch` to PostgREST with the publishable key: the guest menu ships no Supabase client (its JavaScript budget test would fail).
- Why polling and not Realtime: on the Free plan Realtime allows 200 concurrent connections and a fixed message rate, and every guest at every café would hold a socket open for hours; one extra connection per guest also costs battery and reconnect logic on a phone. Polling a read-only function costs about 6 small requests a minute per open tab, none from a hidden one, needs no new moving part, and a pause or sold-out dish appears within about 10 s. Realtime stays for staff screens, which are few and on one screen all day. If a café ever has hundreds of guests at once, the interval can be raised in `src/features/availability/status.ts` or the answer cached at the edge.
- Consequences: `api.public_menu` has three new fields; the app tolerates a database without the migration (no controls, no polling effect, editor loads without hours). The guest sees "Ordering is paused for a few minutes" with the resume time read on their phone, or "The kitchen is closed for today".

## ADR-069: Telegram manager bot (buttons, no AI)

- Status: Accepted, 2026-11-23 (owner spec, Phase 2; free only: Telegram Bot API, no new dependency).
- Context: a manager should change the café (sold out, pause ordering, later price, hide, promo) from Telegram without opening the admin. Only people the owner linked may do it; mistakes must be undoable.
- Decisions:
  1. **Who.** A linked account is an active Telegram `notification_channels` row made with the one-time link code, whose creator is still an active owner or manager. It is found by the chat id stored at linking, nothing else. Only private chats where the sender id equals the chat id count (a linked group is not a bot account). Everyone else gets no answer at all (the old greeting for a bare `/start` and the link replies stay, they are the linking flow). One café per chat: the newest link wins. A café with several locations acts on the location it was linked to, else its oldest.
  2. **Where the rules live.** `private.bot_handle` (Postgres) validates every press and message, keeps the state and applies changes; it returns a *screen* (JSON). The app only draws screens (`src/features/telegram-bot`, typed hy/ru/en dictionary). `api.telegram_update` stays the only client-callable entry, guarded by the webhook secret from Vault (ADR-038); the bot functions are not granted to anyone. No service-role key.
  3. **Replies.** Sent as the webhook's own HTTP answer (one Bot API call, `editMessageText` or `sendMessage`): instant, and the app needs no token. The outbox is not used (10 s cron is too slow for taps). A webhook answer can carry one method, so the "stop the spinner" call `answerCallbackQuery` is sent by the database with pg_net and the Vault token (as the outbox does); a failure there is swallowed.
  4. **callback_data** is a verb letter plus at most one opaque argument (`a:<action>`, `p:<uuid>`, `c:<choice>`, `g:<page>`, `k:<token>`, `l:<lang>`, `m b x u h`), at most 64 bytes. Ids are checked against the account's café; choices against the action's list; the confirm token is random per preview and single use.
  5. **Flow.** Registry `private.bot_actions` (id, steps, choices, ready) + `bot_prepare_/bot_apply_/bot_undo_<id>`. One pending step per chat (`private.bot_pending`, 10 minutes). Nothing changes until the confirm button with the right token; confirming consumes the pending row first, so a repeat does nothing. A number step reads typed text; other text answers with the menu. Lists show 8 per page; a menu over 24 items asks for the section first.
  6. **History and undo.** `private.bot_changes` records who (channel), action, entity, old, new, time, `undone_at`, and undo rows (`undo_of`). Undo (own last change, with confirmation) restores only if the current value still equals the recorded new value, else says it changed. Every change also writes `audit_log` (`bot.<action>`, actor `system`, the linking user). Rate limit: 60 presses a minute per chat, then silence.
  7. **Shared rules.** Pause moved into `private.apply_ordering_pause(location, paused, until, minutes, actor_kind, actor)`; `api.set_ordering_pause` calls it (same behaviour). Sold out uses the stop list with `until` at the end of the business day, as the admin does.
  8. **Language.** Chosen by buttons on first use, stored in `notification_channels.bot_locale` (and `locale`); the menu's Language button changes it.
- Threat model: the webhook secret is the only thing between the internet and these functions, as for linking; a leaked secret lets an attacker send fake updates for any chat id, so it stays in Vault and the route accepts only its header. Changing a chat's rights is only possible via the owner's link code. A manager removed or deactivated loses the bot at once.
- Consequences: re-run `private.telegram_set_webhook` after deploy (adds `callback_query`). Reference actions: sold out and pause; the other menu entries say "coming soon".
- Built 2026-11-23 (migration 20261123160000): price, hide / show, close kitchen early. Decisions: a price change is refused for items with priced options (a base-price change would move every option price); publish and kitchen-close are shared `private` cores with an explicit actor, the api functions keep their checks. Hide / show: the item picker lists active items only, so "show" is not reachable from the bot yet. Still "coming soon": category on/off (the engine has no section step) and today's report (the engine has no read-only path). How to add one: `docs/02-stack/telegram-bot.md`.
- Engine extension 2026-11-23 (migration 20261123170000): a `category` step (sections, 8 per page; before an item step it narrows the list, alone it is the picker), `pick_inactive` (pickers list inactive sections and hidden items, marked off), and a `read` action kind (no steps, no confirm, no history: `private.bot_read_<id>` returns facts shown at once). Built on it: **category on/off** (flips `categories.is_active` like `api.save_category`, then `publish_menu_core` as the linked account; undo restores only if unchanged and republishes), **today's report** (orders, revenue and average bill from `private.day_summary_payload`, the same numbers as the evening summary and test orders / test bills left out; top 5 dishes by quantity), and **show item** (hide / show lists hidden items too). Revenue in the report is the ordered amount, as in the evening summary; the dashboard's revenue counts paid bills only, so they differ while checks are open.
- Add new item and promo on / off, 2026-11-23 (migration 20261123200000). Engine: step kinds `text_<field>` (typed, cleaned, 1 to 80 characters), `promo` and `photo`; `optional_steps` with a Skip button (verb `s`); the webhook also passes photo messages of linked private chats to the bot. **Add new item** follows the admin's create rules (whole price 0 to 10 000 000, Armenian name required, the section must be the café's, active and on this location's menu, translations by `private.set_translations`, no AI flag, no allergens), publishes as the linked account, and undo removes the item or, when orders already mention it, hides it. **Promo** uses `private.apply_promo_on`, the core of `api.set_promo_on`.
- **Photo for new items (decision pending; the step is OFF).** A photo reaches the bot as a Telegram `file_id`. Storing it means downloading it (Bot API `getFile`, then a URL that contains the bot token) and writing it to the `menu-images` bucket (path `<restaurant>/items/<item>/<n>.<ext>`, 2 MB limit, jpeg, png, webp), which the Storage API only accepts with a user's JWT or the secret key. Options, evaluated:
  - A. Only the database, with pg_net and the Vault token: **not possible**. pg_net sends JSON bodies and keeps response bodies as text, so bytes cannot be fetched or uploaded intact, it is asynchronous, and the Storage write still needs a key. No migration alone can do it.
  - B. The Next.js route downloads and uploads: needs `TELEGRAM_BOT_TOKEN` as a Vercel env var (the owner adds it) and an upload right for the app, either the secret key (forbidden, ADR-038) or a narrow Storage policy letting the publishable key write one pre-authorized path. It reverses ADR-038 point 4 for the token.
  - C. A Supabase Edge Function (recommended): the database calls it with pg_net and the webhook secret (`file_id`, item id); the function reads the token from an Edge secret (`supabase secrets set`, owner), downloads the file, uploads it to Storage with the key Supabase gives Edge Functions automatically, and calls a definer function that sets `items.image_path` and republishes. The token and key never reach Vercel, ADR-038 stays as written, free plan (500 000 invocations a month). Telegram photos are already JPEGs of at most 1280 px, so no resizing is needed. What is needed: the owner sets the Edge secret, a CI step deploys the function, then the Vault secret `bot_photo_enabled` = `on`.
  - D. Photo in the admin only (today): the bot says nothing about photos and the manager adds one in the editor. Nothing to build or approve.
  Recommendation: C when photos from the bot matter; D until then. The database half is built (step, flag, size limit, `private.bot_photo_jobs` queue); the worker and the function that finishes a job are not.

## ADR-070: Promotions are a banner, not a price change

- Status: Accepted, 2026-11-23 (owner decision on "Promo on/off"; free only, no new dependency).
- Context: owners want to announce something ("Happy hour", "New summer menu") to guests and switch it on and off, also later from the Telegram bot. A real discount engine (prices, rules, stacking, tax) is a different and much larger feature.
- Decisions:
  1. **A promo is an announcement.** A title (hy required, ru and en optional), an optional one line, an optional badge text ("−20%") and an optional start and end. It never changes a price or a bill; the waiter applies any discount. The waiter app shows one line, "Promo on: <title>", so they know what to apply.
  2. **Data.** `public.promos` per location, up to 3 (the owner may keep several prepared, any number on). Texts are `jsonb` by language like the rest of the snapshot. `starts_at`/`ends_at` are `timestamp` in the café's wall-clock time and are compared with `now() at time zone locations.timezone`, so a promo starts and ends by itself. Owners and managers read the table through RLS; guests and staff logins cannot.
  3. **Who and how.** `api.save_promo`, `api.set_promo_on(promo, on)` (returns whether guests see it now) and `api.delete_promo` are `SECURITY DEFINER`, `search_path = ''`, check `private.assert_location_role(..., '{owner,manager}')`, write `audit_log`, and are executable by `authenticated` only. The bot's engine calls `api.set_promo_on`.
  4. **What guests read.** `private.live_promos(location)` (on and inside the window) is returned as `promos` by `api.public_menu` and `api.public_menu_status`. The existing 10-second poll (ADR-068) compares it with the page, so a switch shows within about 10 s without a reload.
  5. **Banner.** At the top of the guest menu, in the guest's language with Armenian as the fallback, in the café's theme tokens, a 44 px close button that lasts for the visit (`sessionStorage`; a new promo shows again). About 1 KB of JavaScript, inside the guest budget.
- Consequences: the app tolerates a database without the migration (no section in the admin, no banner, status without `promos` reads as none). The admin lives in a "Promotions" section on the admin home under "Guest orders". If real discounts are wanted later they need their own ADR (pricing rules, order lines, reports); this table would then link to them rather than grow price fields.

## ADR-071: Problem tables in real time

- Status: Accepted, 2026-11-23 (owner spec 3.5; free only, no new dependency).
- Context: owners want to know when a table waits too long for its food, or keeps calling the waiter with no answer. The kitchen already raises `order.overdue` for tickets cooking longer than 20 minutes; that is about the kitchen, not about the guest's wait.
- Decisions:
  1. **Two conditions.** *Slow*: an accepted order, not served, not paid, not a test order, placed more than `locations.overdue_minutes` ago (default 25, 5 to 180) and less than 6 hours ago (older ones are forgotten, not late). *Calls*: an open `call_waiter` request with `press_count >= locations.repeat_call_threshold` (default 3, 2 to 10). "Bring the bill" never alerts.
  2. **Counting presses.** A repeat press collapses into the one open request (`service_requests_one_open`), so presses are counted on it: `service_requests.press_count` and `last_pressed_at`, updated by `private.count_service_press` from `api.guest_service_request`. A tap within 5 seconds of the last one is a double tap and is not counted; counting stops once a waiter acknowledges the request; the count is capped at 99. A new request after resolving starts again at 1.
  3. **No alert table.** The list is computed (`private.table_alerts_live`) from orders and requests, so an alert disappears by itself when the order is served or the request is acknowledged or resolved. `api.table_alerts(location)` returns it to owners, managers and waiters of that café only.
  4. **Sending.** The minute job (`private.run_alert_checks`, pg_cron `pativ-alerts`) calls `private.enqueue_table_alerts`: one outbox row per chat per condition (`table.alert:slow:<order id>`, `table.alert:calls:<request id>`), so no repeats. A new event `table.alert` joins `private.alert_events()`, is on by default and was added to chats that already receive `order.overdue`. Texts in hy, ru and en come from `private.render_notification` (a new layer in front of the existing ones). Worst-case delay is the one-minute job. No bot buttons.
  5. **Who changes the limits.** `api.set_alert_settings(location, minutes, calls)`: `SECURITY DEFINER`, owner or manager of that café only, validated, written to `audit_log` (`alerts.settings`), executable by `authenticated`.
  6. **Screens.** The admin home has an "Attention needed" list and an "Alerts for slow tables" form (two numbers). Both poll `api.table_alerts` every 15 seconds while the tab is visible (the availability pattern, no realtime channel). The waiter app shows the same list as a strip under the header, and nothing when there is no problem.
- Consequences: the app reads these through separate calls, so a database without the migration shows no panel and no form (the Telegram toggle for the new event needs the migration, because the database validates the list). The old `order.overdue` (kitchen, 20 minutes, fixed) stays; an owner who finds the two alike can switch it off per chat. Slow orders are measured from `placed_at`, in absolute time, so the café time zone does not change the result.

## ADR-072: Guest event tracking without personal data

- Status: Accepted, 2026-11-23 (owner spec, Phase 3.1; free only, no new dependency). Number 072 because 071 is on `origin/claude/new-session-qjsyvc`; renumber at merge if another ADR took it.
- Context: owners (and the later "goes well with" recommendations) need to know which dishes guests look at, add, abandon and accept as suggestions. Order, kitchen and waiter times already exist in the database. The guest menu must stay light and ordering must never depend on analytics.
- Decisions:
  1. **Privacy.** No name, phone, e-mail, IP address or user agent is stored, and the table has no column for any of them. The only identifier is an anonymous session key: the table's guest session id when the phone has one (`pativ:guest:v1:<table>`), else a random id kept in `sessionStorage` for the visit. `meta` allows only the keys `from` (a dish of the same menu), `qty` (1-2 digits) and `via` (up to 16 characters); anything else is refused. The tracker respects Do Not Track and Global Privacy Control (sends nothing).
  2. **Four guest kinds, stored.** `item_view` (dish sheet opened), `item_add`, `suggestion_shown`, `suggestion_accepted` (the "often added" pairs in the dish sheet, with `meta.from` the dish being viewed). Order, accept, ready, served, waiter call and bill request are not copied: `orders.placed_at / accepted_at / ready_at / served_at` and `service_requests.created_at` are the record. `served_at` is stamped when the last ticket is served (`kitchen_tickets` status change, trigger `sync_order_kitchen_status`) and by `api.set_ticket_status`, so no new column was needed.
  3. **One place for reports.** `api.event_timeline(location, from, to, limit)` unions guest events with those timestamps as `order_placed`, `order_accepted`, `order_ready`, `order_served`, `waiter_called`, `bill_requested`. It is a function that checks owner or manager of the restaurant (a view would run with its owner's rights and skip RLS; the RLS coverage test forbids views). Range at most 31 days, 5 000 rows.
  4. **Abandoned is derived, never stored.** `cart_abandoned` is emitted for an `item_add` when the same session added nothing more in the next 30 minutes and placed no order in that time, at the add plus 30 minutes, and only once that time has passed. An order links to events by `orders.guest_session_id = session_key`, so a phone that browsed with a random visit key and then joined a table changes key and counts as abandoned for the earlier adds: the figure is an upper bound.
  5. **Write path.** `api.record_guest_events(location, session, events)`, `SECURITY DEFINER`, `search_path = ''`, executable by `anon` and `authenticated`. It needs an active café with a published menu (menu-only cafés are tracked too; it does not require ordering to be on), at most 20 events per call, a kind from the allowlist, and every `item_id` (and `meta.from`) in the published menu snapshot of that café. A client time is ignored (`at` is `now()`). One bad event refuses the whole call. Errors are plain codes (`guest_events_bad_kind` and so on) and nothing sensitive is returned (`{recorded: n}`).
  6. **Rate limit.** 60 events per minute per session and 1 200 per minute per café, counted on the rows already stored (indexed), so no counter table is needed. A refused call writes nothing. A bot with new session ids is stopped by the café cap and can at worst fill one café's minute quota; it cannot grow the table faster than 1 200 rows a minute for that café.
  7. **Batching.** The app queues events in memory and sends them every 5 s, when 20 are waiting, and when the page is hidden, as one call; this is 1 request per several taps instead of one per tap (free-plan connection and write budget). A repeated view of the same dish within 30 s is one event. Sent with `fetch` and `keepalive` rather than `sendBeacon`: the `api` schema needs the `Content-Profile` header and the key needs the `apikey` header, and a beacon can set neither. A failed send is dropped (never retried, never shown). The tracker module loads lazily on the first event; the guest bundle holds only a few-byte stub.
  8. **Retention and size.** A row is about 250 bytes with its indexes (location + time, dish + time, session + time, and a BRIN on time for the purge). A busy café with 150 visits a day at about 25 events a visit writes about 3 750 rows a day (about 0.9 MB), so about 85 MB over 90 days. `private.purge_guest_events()` deletes rows older than 90 days in batches of 5 000 so a night's job never holds a long lock or a large single write; `pativ-purge-guest-events` runs daily at 02:50 UTC where pg_cron exists.
- Consequences: the app tolerates a database without the migration (the call fails and is dropped). `src/lib/supabase/types.ts` has the table; `api.*` functions are not in the generated types yet. The e2e spec skips until the migration is on the dev project. A later recommendations job reads `suggestion_*` and `item_*` through `api.event_timeline` or the table (owner and manager only).

## ADR-075: Game rewards, owner-controlled

- Status: Accepted, 2026-11-23 (owner spec 4.1; free only, no new dependency, no AI, no payments, no change to game characters or art).
- Context: guests play the waiting-room games (ADR-059) while their order is prepared. An owner may want to thank them: "reach level N, get 10% off" or a free promo line. Off unless the owner switches it on.
- Decisions:
  1. **Settings in their own table.** `public.game_reward_settings` (one row per location; no row means off): `game_rewards_on` (default false), `reward_kind` (`percent` or `text`), `reward_level` (2 to 50), `reward_percent` (1 to 50) or `reward_text` (hy/ru/en, hy required for a text reward, 80 characters), `reward_game` (null: any of the five games, or one game id). A separate table, not `locations` columns, keeps the guest-readable location row unchanged. Owner and manager read it through RLS; only `api.set_game_rewards` writes (`SECURITY DEFINER`, `private.assert_location_role` owner or manager, validated, `audit_log` `game_rewards.updated`).
  2. **What "level" means.** The games count score, not levels (only the platformer has rooms, three of them). The host turns a score into a level: `1 + floor(score / step)` with a step per game (`POINTS_PER_LEVEL` in `src/features/games/rewards.ts`: runner 50, fighter 100, merge 200, slice 30, platformer 300). The games themselves are untouched. The steps are a first guess; change them in one place once real scores are known (the owner's level N then keeps its meaning).
  3. **How a guest is authenticated.** Exactly like `api.guest_service_request`: the caller is a signed-in anonymous user (`authenticated`, `anon` has no grant), passes their `guest_session_id`, and the function checks that the session is theirs, live, and the table (QR version) and café are still valid (`private.reward_guest`). The order must belong to that guest session.
  4. **Claim.** `api.claim_game_reward(guest_session, order, game, level)`. Idempotent: one row per order (`game_reward_claims.order_id` unique); a repeat returns the same reward, even after the owner switched rewards off or changed them (the reward is a snapshot). New claims need: rewards on, the game eligible, `level >= N`, level at most 100, order `placed` or `accepted` and not served or paid, order at least 15 seconds old, and at most 10 claim attempts per guest session per 10 minutes. The level is reported by the phone and can be faked; that is accepted because the waiter looks and applies the reward, and the checks keep the damage to one reward per order.
  5. **Guest reads.** `api.guest_game_reward(guest_session, order)` returns the offer (when on) and the guest's own claim. Guests have no access to the two tables. `api.public_menu*` is not touched, so the menu payload and bundle stay as they were.
  6. **Guest screens, lazily.** The reward display is two small lazy chunks (about 2 KB gzipped each): a note under the games on the order-status page (the offer, and once earned, the reward, kept while the order is open and reloaded after a claim) and an overlay inside the game layer (one quiet goal line, then a calm card with the reward and "Got it"; hidden while the "order ready" banner is up). Nothing loads for the menu, and nothing about the game art changes.
  7. **Waiter.** `public.game_reward_claims` is readable by staff of the location (RLS `my_location_ids`). The waiter app lists the open claims of a table in the table panel and on the bill (settle) sheet: "Reward earned: 10% off (level 5)", with Applied and Dismiss (48 px) until handled; claims older than 12 hours are not listed. `api.resolve_game_reward(claim, 'applied'|'dismissed')` is for owner, manager, waiter and cashier of that café, idempotent for the same answer, refuses the opposite one (`RS409`), writes `audit_log` (`game_reward.applied` / `.dismissed`) and broadcasts a `reward` message on `loc:<id>` so other tablets refresh.
  8. **"Applied" does not change the bill.** There is no function that adds a discount to a bill yet (`bill_discounts` exists in the schema with no writer). "Applied" records that the waiter gave the reward, and who; the waiter gives the discount or the item by hand, as with promotions (ADR-070). A real bill discount is a later step.
  9. **Admin.** A "Game rewards" section on the admin home: a switch, reward type (percent or gift), level, percent or the three-language text, which game, one Save button (44 px and up, usable at 360 px). A database without the migration hides the section.
- Not done: a claims count in the dashboard (skipped: not trivial next to the existing dashboard function); per-game level steps tuned from real scores; a discount line on the bill.
- Consequences: new migration `20261123220000_game_rewards.sql`, SQL tests `supabase/tests/sql/game_rewards.sql`, unit tests for the level and wording logic, one e2e spec that skips until the migration reaches the dev project. The app tolerates a database without the migration: the offer call fails quietly (no note, no overlay), the waiter's read returns nothing, the admin section is hidden.

## ADR-073: Owner reports from collected data

- Status: Accepted, 2026-11-23 (owner spec, Phase 3.2-3.4; free only, no new dependency, no AI). Number 073 because 072 is the latest on this branch; renumber at merge if another ADR took it.
- Context: owners want to know which dishes are looked at but not ordered, when the café is busy or dead, how long tables stay, and whether the "often added together" suggestions work. The data exists (`guest_events`, orders, bills, table sessions). The weekly Telegram digest must reuse exactly the same numbers.
- Decisions: three read-only functions, all `SECURITY DEFINER`, `search_path = ''`, `private.assert_location_role(location, '{owner,manager}')` (waiter and kitchen logins, other cafés and guests get `forbidden`), range 1 to 92 days (`invalid_range`), executable by `authenticated` only. Migration `20261123230000_owner_reports.sql`, tests `supabase/tests/sql/owner_reports.sql`. No `anon` function was added, so the `rls_coverage` allowlists did not change (its catalog checks still pass).
  1. **Period.** Business days in the café's calendar. Orders and bills use `business_date`; events have only a time, so they are cut at `business_day_starts` in the café's time zone (`[from + start, to + 1 day + start)`).
  2. **Test data.** Orders with `is_test` are excluded everywhere; paid bills whose table session has orders and only test orders are excluded, as in `api.sales_dashboard` (ADR-066). Guest events carry no test flag and count as recorded.
  3. **`api.item_conversion(location, from, to)`.** Per active dish with views or orders: `views` (`item_view`), `adds` (`item_add`), `orders` (units on accepted, non-test, QR orders, cancelled units removed), `conversion = orders / views` capped at 1, null without views. Only QR orders count because only a guest on a phone can have viewed a dish before ordering it; waiter orders would raise the share for no reason. **Highlight rule:** flagged when the dish has at least 20 views and either no orders (`never_ordered`) or a share below half the café's median (`low_share`). The median is over dishes with at least 5 views, and only when 3 or more qualify; otherwise only `never_ordered` is flagged. Dishes under 20 views are `few_views`, the rest `ok`. The reason is data: `{key, views, orders}`; the app turns the key into a sentence (`messages/*.json`, `reports.conversion.reason.*`), SQL returns no text. Sorted: flagged first, then most views. Result also carries `median` and `min_views`.
  4. **Menu engineering wording.** The class code stays `plowhorse` in `api.menu_engineering` (no API change). The UI names the four classes Stars, Workhorses, Puzzles, Dogs (`insights.matrix.<class>.name`, hy/ru/en) above the existing plain-language title. Known gap: a section where not every dish has a cost price is ranked by price (a notice says so), not "popularity only" as the owner spec words it; changing that means changing the matrix itself and was left alone.
  5. **`api.busy_hours(location, from, to)`.** `cells` per local ISO weekday (1 = Monday) and hour: `orders` = accepted non-test orders by `placed_at` hour (as `sales_heatmap`); `revenue` = total of paid bills by the hour of `closed_at`, with the dashboard's filters, so the cells sum to the dashboard's revenue for the same days (the dashboard counts revenue from paid bills, not orders; a café that never marks bills paid shows 0 revenue). `weekday_days` says how many of each weekday the period holds; the UI shows the average per such day (total / days), so a week and a month are comparable. **Table time:** average minutes from `table_sessions.opened_at` to `closed_at`, overall and by weekday opened, for closed sessions opened in the period that have at least one accepted non-test order and lasted under 8 hours (a table left open overnight is a forgotten close, not a visit).
  6. **`api.upsell_report(location, from, to)`.** `shown` and `accepted` are the `suggestion_shown` and `suggestion_accepted` events; `accept_rate = accepted / shown`, capped at 1, null when none were shown. `orders_with_suggestion`: accepted, non-test orders whose `guest_session_id` equals the event's `session_key`, placed within 2 hours after the acceptance, that contain the accepted dish; each order counts once. `revenue`: the line totals (after cancellations) of those dishes in those orders, each line once. Revenue is derivable, so it is given; both are lower bounds, because a phone that used a random visit key before joining a table cannot be tied to an order (ADR-072, point 4). `pairs`: the five most shown "dish being viewed to suggested dish" pairs with names.
  7. **UI.** `/admin/reports` (navigation item "Reports"), owner and manager. Period: the dashboard's `RangePicker` (presets and dd.mm.yyyy dates for hy and ru), default last 30 days; orders or revenue for the busy-hours grid is a `?metric=` link, no JavaScript. Sections: Viewed but not ordered (a highlighted group above the other dishes), Menu engineering (the existing matrix), Busy hours (grid, orders or revenue, table time), Suggestions. Each section loads on its own: a database without the migration shows a notice for it, never a failed page. Plain CSS and tables, no chart library.
  8. **For the weekly digest.** Call the same three functions with the digest's period; use `flagged` items and the reason keys, `cells` and `table_time`, and the `upsell_report` totals. Do not recompute the rules elsewhere.
- Consequences: `src/lib/supabase/database.ts` was extended by hand with the three functions (`npm run db:types:api` fails on the `event_timeline` table-returning function from ADR-072; fix the generator when next needed). The e2e spec `tests/e2e/reports.spec.ts` skips until `E2E_REPORTS_MIGRATION=applied`.

## ADR-076: Ingredients, substitutes and "ingredient out"

- Status: Accepted, 2026-11-23 (owner spec "A. Missing ingredients: substitutes or auto-hide"; free only, no AI, no new dependency).
- Context: when an ingredient runs out, staff should do one thing and the guest should never read "we ran out". The tables `ingredients` and `recipe_lines` existed in the baseline with no screen or function using them.
- Decisions:
  1. **Model.** `ingredients` gains `name_i18n` (`{"ru","en"}`; `name` stays the Armenian one; a missing language falls back to it) and `kcal_per_100g` (for the later calories feature). `recipe_lines` gains `is_key`, `substitute_ingredient_id` (same café by composite foreign key) and `substitute_price_delta` (AMD, may be negative, null = no price change). "Replaceable" simply means a substitute is set; only a key line of a dish may have one. `public.ingredient_catalog` is a read-only list of about 100 common ingredients (names in three languages, unit, approximate kcal from public nutrition tables) that owners copy from through `api.ingredient_catalog` and `api.add_catalog_ingredient`; the table itself has no client grant.
  2. **Outage.** `public.ingredient_outages` has one row per location and ingredient with `until` = the next business-day opening, computed like the stop list and the closed kitchen (`private.business_day_end`: `business_day_starts` in the café's time zone). It is active while `until > now()`, so it ends by itself with no job; a nightly job only deletes rows older than two days. `api.set_ingredient_out(location, ingredient, out)` may be called by the people who may change the stop list from the kitchen screen: owner, manager, kitchen and waiter logins of that location. The rule lives in `private.apply_ingredient_out` (with the actor kind and the channel `kitchen` / `bot` / `admin`) so the Telegram bot calls the same code. `api.search_ingredients` finds the café's ingredients by a case-insensitive substring over all three names (plain `lower()`; the `unaccent` extension is not installed), most used in recipes first, at most 30, with an `is_out` flag.
  3. **Effects (live overlay, not a republish).** The published menu is an immutable snapshot; outages change within minutes, so they are applied on top when the menu is read, exactly like the stop list. `private.outage_effects` decides per dish from its key lines: a key ingredient out with no substitute, or whose substitute is out too, or more than one key ingredient needing replacement (one note per dish) hides the dish; one active replacement is a substitution. `private.outage_overlay` turns that into one JSON that the menu, the status and the order all read, so they cannot disagree.
  4. **Hide or show "sold out".** `locations.out_ingredient_display` is `'hide'` (default: the dish is removed from the menu answer, so a cart that holds it marks it unavailable) or `'sold_out'` (the dish stays and its id joins `sold_out`, so the existing label shows). Owners and managers change it with `api.set_out_ingredient_display`.
  5. **What guests read.** `api.public_menu` and `api.public_menu_status` keep their old bodies as `private.public_menu_base` and `private.public_menu_status_base` and wrap them (a later migration that changes the menu answer changes the base; replacing the public function would drop the overlay, and a SQL test would fail). While an outage is active the menu answer carries `outages` (a short hash of the overlay, also in the status, so open menus reload within one 10-second poll) and, for substituted dishes, `substitutions: {<item id>: {from: {id, name: {hy,ru,en}}, to: {id, name: {hy,ru,en}}, price_delta}}`; `menu.items[id].price` already includes the difference. Nothing is added when nothing is out.
  6. **The order.** In `private.place_order_core` a hidden dish is refused with the existing `item_unavailable` (`item_sold_out` in the 'sold_out' display mode), and a substituted dish stores `order_items.substitution` (the same `{from, to, price_delta}`) and the price difference in `unit_price` (clamped at 0), so `line_total` and the order total include it. Waiters get the substitution without a question. For guests, `api.guest_place_order` and `private.place_guest_order` gain an optional last parameter `p_subs_ack jsonb` (default null): a JSON list of the `from` ingredient ids whose substitution the guest saw and accepted. An active substitution on an ordered line that is not in the list is refused with `substitution_changed`; the error detail is a JSON list of `{item_id, from, to, price_delta}` so the screen can ask again. A missing `p_subs_ack` with no active substitution behaves exactly as before, a retry of an order already placed is returned without the question, and the old function signatures are replaced (one name for PostgREST). Guest choice is final; being informed is the point of the acknowledgement.
  7. **Kitchen and waiter.** The order line (`order_items.substitution`) reaches the kitchen board and the waiter queries; the kitchen ticket shows "Use <ingredient>" under the dish in the kitchen's language. The reads use `order_items(*, ...)` so they keep working before the migration reaches a project.
- Consequences: all rules are in Postgres and tested (`ingredients_substitutes.sql`). Until the guest pop-up exists the guest client sends no `subs_ack`, so a dish with an active substitution cannot be ordered (the menu reloads and shows the note); the pop-up task must send `subs_ack` and show `substitutions`. Recipes and key lines are live data: editing them needs no republish. Costs and calories can use the same recipe lines later.

## ADR-074: Weekly Telegram digest, chosen by rules

- Status: Accepted, 2026-11-23 (owner spec, Phase 3.6; free only, no new dependency, no AI at runtime). Number 074 because 073 is the latest on this branch; renumber at merge if another ADR took it.
- Context: owners rarely open reports. One short message each Monday should say what to look at, in their language, from numbers the reports already compute (ADR-073), without any language model.
- Decisions (migration `20261123260000_weekly_digest.sql`, tests `supabase/tests/sql/weekly_digest.sql`):
  1. **Cores.** `api.item_conversion`, `api.busy_hours`, `api.upsell_report`, `api.menu_engineering` keep their caller check and results and now call `private.*_core` functions (same bodies, no `auth.uid()` check), so the cron job runs the same maths and nothing is re-implemented. `menu_engineering_core` takes `p_owner`; the digest passes `false`, so no cost price ever reaches a message (managers read it too; the matrix then ranks by price).
  2. **Engine.** `private.weekly_digest_candidates(location, from, to)` lists every rule that fires, with a score; `private.weekly_digest_payload` keeps the best three, one per rule type, a dish at most once (the next candidate takes its place). Tie: higher score, then the rule order below, then the dish id. Output is data only: `findings[i]` and `actions[i]` are keys plus numbers (`{key, item{hy,ru,en}, views, orders, ...}`); the words live in the renderer. Test orders are excluded (the cores do it); the period is seven business days Monday to Sunday.
  3. **Rules, thresholds, scores** (score = base + bonus; a finding is only emitted when its numbers meet the threshold, so each sentence is true by construction):

     | Rule (finding, action) | Fires when | Score |
     | --- | --- | --- |
     | unordered, check photo or price | the most viewed dish `item_conversion` flags (20+ views, never ordered or under half the median share) | 80 + views/10 (max 20) |
     | wow_up / wow_down, keep stock / see Reports | orders (revenue when both weeks have paid bills) moved 15 % or more against the week before, which had 20+ orders | 60 + abs(percent)/2 (max 30) |
     | slow, check kitchen pace at the hour | 3 or more of: orders served later than the café's limit (`overdue_minutes`, default 25), "call waiter" requests with at least `repeat_call_threshold` presses; the hour is the one with most of them | 75 + count (max 20) |
     | workhorse, small price rise | popular class `plowhorse` with 10+ units; the most ordered | 70 + units/5 (max 20) |
     | puzzle, move up or promote | class `puzzle`, its section sold 30+ units; the highest price | 65 + price/200 (max 20) |
     | dog, remove or rework | class `dog`, its section sold 30+ units; the fewest units | 60 + section units/20 (max 20) |
     | busiest, plan an extra waiter | the weekday-hour with the most orders, at least 6 and 10 % of the week | 55 + orders/3 (max 20) |
     | dead, consider a promotion (Promotions) | an hour strictly inside the week's opening range (5+ hours), with 20 % or less of the hourly average orders | 50 |
     | suggest_high / suggest_low, add or review suggestions | 30+ suggestions shown and accepted at least 20 % or at most 5 % | 45 + shown/10 (max 15) |

     "Price" in workhorse, puzzle and dog is the `menu_engineering` margin on its price basis (no costs, point 1): a workhorse is popular and priced below its section's sales-weighted average, a puzzle priced above it and rarely ordered. If no rule fires the message says nothing stands out.
  4. **Enough data.** At least 20 orders in the week. Under that: no findings. A short "not enough data yet" goes only to a chat that is new (linked in the last 14 days) and has had no digest; every later quiet week is skipped silently, so nobody gets a monthly apology.
  5. **Schedule.** pg_cron job `pativ-weekly-digest`, every 15 minutes, `private.enqueue_weekly_digests(now())`. A café is due on its own Monday between 09:00 and 12:00 local time (the window survives a missed run; a café whose business day starts after 09:00 waits for it). Once per ISO week: outbox `unique (channel_id, dedupe_key)` with key `weekly.digest:<location>:<ISO week of that Monday>` (e.g. `2026-W43`), so repeated runs, retries and late-linked chats never double-send; a chat linked the same morning gets it at the next run. The week reported is the one that ended on Sunday. A row older than 6 hours is dropped by the sender (existing rule), so a long outage skips the week instead of sending it on Tuesday.
  6. **Delivery.** New event `weekly.digest` (`private.alert_events()`, the column check and default, the owner's per-chat toggle in notification settings with hy/ru/en labels; existing chats that get late orders were switched on). Only Telegram chats, active, with the toggle on, linked by a person who is still an active owner or manager (a waiter's chat or a removed manager's chat gets nothing); the toggle is hidden on phone-notification cards. The text is rendered per chat in its language by `private.render_notification` (one more layer, like ADR-071): a header with the period, orders and revenue, up to three numbered findings each followed by `→ action`, a footer pointing to Reports. Plain text, no parse mode, so a dish name cannot break it; names are cut at 60 characters; the whole message stays under 1 500 characters (Telegram allows 4 096). Emoji: one in the header, arrows.
  7. **Reports page.** `api.last_weekly_digest(location, locale)` (owner and manager) computes the last complete Monday to Sunday week with the same payload and renderer and returns the message text; the page shows it as a plain card "Last week's summary". Nothing is stored. A database without the migration shows no card.
  8. **Privacy.** The payload holds dish names, counts and prices only: no guest, session, device or staff data. The sender sees the same text the owner sees. Costs never appear.
- Consequences: one more cron job (free tier, 96 cheap runs a day; the heavy work happens only in the Monday window and only for cafés with a due chat). `rls_coverage` needed no change: the new functions are `private` (revoked from clients) except `api.last_weekly_digest`, which only `authenticated` can run and which checks owner or manager; the anon and authenticated allowlists are unchanged and still pass. Known limits: "slow" counts orders that were served late, not orders never served; a week with fewer than 20 orders in the week before gives no comparison; the thresholds are fixed, not per café.

## ADR-077: "Goes well with" recommendations, rule-based

- Status: Accepted, 2026-11-23 (owner spec "B"; free only, no AI, no external service). The guest screen that shows the ideas is a later task; this ADR covers data, rules, the read function and the owner editor.
- Decisions:
  1. **Kinds.** `items.item_type` (domain `public.item_type`: coffee_tea, cold_drink, alcohol, breakfast, starter_salad, soup, main, side, sauce, dessert, pastry_snack; null = unknown). `api.set_item_type` sets it (owner/manager). `api.suggest_item_types(location)` only proposes, from keywords (hy/ru/en) in the section name (`private.guess_item_type`); the owner reviews and applies in the editor.
  2. **Compatibility table.** Global defaults in `item_type_compat_defaults` (18 allowed pairs, the owner's table: a missing pair means "never"), per-location changes in `item_type_compat` (`api.set_compat_rule`, `api.reset_compat_rules`, `api.compat_matrix`). A change equal to the default is not stored.
  3. **Owner pairings.** `item_pairings` (dish to dish, at most 6 per dish, `api.set_item_pairing` / `remove_item_pairing`) and `suggestion_rules` (from category or kind to category or kind, at most 30 per café). Time rules: `suggestion_time_rules` (location, window in the café's time zone, optional ISO weekdays, a kind or a dish, at most 10; a window past midnight uses the weekday it began). The editor leaves rules and time rules out for now; the functions are tested.
  4. **Owner pairings bypass the table** (the owner decided); everything else obeys it. With a typed dish only allowed kinds pass; a candidate without a kind cannot be checked and is dropped. An untyped dish gets no table-based ideas, only owner pairings, time rules and learned pairs (nothing to check against).
  5. **`api.public_suggestions(location, item, cart)`** (anon-callable, ids and reason keys only, any invalid input gives an empty list). Candidates, best tier first: 1 owner pairings (`pairs_with_dish`), 2 category/kind rules (`perfect_with_type`, or `pairs_with_dish` for a section rule), 3 time rules (`time_rule`), 4 learned pairs (`often_together`, same logic as ADR-060 through `private.learned_pairs`, now shared with `api.public_menu_hints`), 5 the table itself (`perfect_with_type`, allowed kinds, dishes ordered most in 60 days first). A dish is never suggested when it is not on the published menu, inactive, on the stop list, blocked by an ingredient outage (`private.outage_effects`, ADR-076), in a closed section window, in the cart or the dish just added. Max 3, at most one per kind (a dish without a kind counts as its own kind).
  6. **Deterministic order:** tier, then rule sort (or learned count, or popularity), then menu sort, then id. Same input, same answer.
  7. **Addendum, speed (migration `20261123330000_suggestions_speed.sql`).** The guest strip timed out now and then (cold 0.5 to 5 s against a 3 s role timeout). Measured on the dev project: the sections of every café were scanned on each call (66 ms), the outage query ran even with no outage (25 ms, 440 to 700 buffers), and learned pairs and popularity re-read 60 days of orders. Now `private.learned_pair_cache` and `private.item_popularity_cache` (per location, no client access) are rebuilt every 15 minutes by `private.refresh_suggestion_caches()` (pg_cron `pativ-refresh-suggestion-cache`, once per café per run, idempotent). `private.learned_pairs` and `private.item_popularity` read the cache and fall back to the live computation (`*_live`, same rules) for a café with no cache row yet. The strip may lag the newest orders by up to 15 minutes. Sections are joined by café, the outage query runs once and only while an outage is active. Output and rules are unchanged. **"Only one per type" is by design** (rule 5): a dish paired by hand with an espresso and a cappuccino shows only the first, because both are `coffee_tea`.
- Consequences: all rules are in Postgres and tested (`recommendations.sql`). The page `/admin/menu/pairings` reads through untyped calls until the API types are regenerated, and shows a neutral notice on a database without the migration.

## ADR-078: Ingredient out in the Telegram bot, and the next-morning question

- Status: Accepted, 2026-11-23 (owner spec A, bot part; free only, no AI, no new dependency). Number 078 is the next free one on this branch; renumber at merge if needed.
- Context: ADR-076 made "ingredient out" a rule in Postgres (`private.apply_ingredient_out`, built to be bot-ready). A manager away from the kitchen should be able to use it from Telegram, and should not have to remember to undo it: an outage already ends with the business day.
- Decisions (migration `20261123280000_telegram_bot_ingredient_out.sql`, tests `supabase/tests/sql/telegram_bot_ingredient.sql`):
  1. **Action `ingredient_out`** (menu entry before Help). One engine step kind `ingredient` is both the paginated picker (8 a page, most used first, same order as `api.search_ingredients`) and the typed search: while it is asked, text of 1 to 40 characters (cleaned like the other text steps) filters the list by plain case-insensitive substring over the three names. The matching is one private function, `private.search_ingredients_core`, which `api.search_ingredients` now calls too (same result, at most 30). Up to 8 matches per page appear as buttons; no match shows an empty list with a "whole list" button. Ingredients already out are marked; tapping one offers "back in". (The spec called the typed step `search`; it is part of the `ingredient` step, so one pending row serves both and Back works in one direction.)
  2. **Same effects as the kitchen.** Apply calls `private.apply_ingredient_out(location, ingredient, out, 'bot', 'system', linking user, member)`; hiding, the substitute note and the live menu update come from the overlay (ADR-076) and need no publish. The result gives counts only: hidden dishes and dishes with a substitute, for dishes whose key line uses that ingredient. Staff-facing, so "out" wording is used; nothing here reaches guests. History row (`bot_changes`), audit entry, and undo only if the current state still equals what the bot set (someone else changing it wins).
  3. **Never trusted.** The picked id is checked against the café's active ingredients in the engine and again in prepare, apply and undo; `ing_out` is set by the engine from the state at the pick; a forged `p_data` with another café's id raises `forbidden`.
  4. **Morning question.** Only for an ingredient that was out yesterday: an outage row ended at the opening that started today's business day (within 20 hours before it, so rows of earlier days are ignored) and has not been set again (a re-set row has a later end). Job `pativ-bot-ingredient-morning`, every 5 minutes, acts only in the first 30 minutes of the café's business day; at most 10 ingredients per café, most used first. One row in `private.ingredient_morning_prompts` per location, ingredient and business day guards against asking twice and holds the answer; the outbox unique key per chat does the same per chat. A question already answered is not sent to other chats.
  5. **Who gets it.** Telegram chats that the bot itself accepts (active, linked by a still active owner or manager, the chat's newest link, this location) and that chose a language in the bot, in that language. There is no new alert toggle: the question belongs to the bot, and the person can switch the bot off with /stop.
  6. **Buttons.** The outbox sender (`private.deliver_outbox`, redefined with one change) adds an inline keyboard to `ingredient.morning` messages: `y:<ingredient id>` and `n:<ingredient id>`, built from the id in the payload only, symbols as labels (no language needed). Both verbs go through `private.bot_handle`: the question must exist for the chat's café and today's business day and be unanswered; the id must be an active ingredient of the café. Yes ("back"): nothing changes. No: the outage is set again for today through the same core, with a history row and undo; if it is already out nothing is written. The message turns into the usual screens (editMessageText).
  7. **Retention.** `purge_old_outages` deletes rows two days after they end, so yesterday's rows are still readable the next morning; nothing changed there.
- Consequences: `private.bot_list`, `bot_next`, `bot_handle`, `deliver_outbox` and `render_notification` (a new wrapper layer `render_notification_ingredient`) are replaced again; a later migration that replaces them must start from these. Known limits: the question is asked only in the first 30 minutes of the day (a chat linked later is not asked); a café whose business day starts at midnight is asked at 00:00 to 00:30 local time; texts in the morning message live in SQL (like the digest), the bot's own screens in `texts.ts`.

## ADR-079: Guest page JavaScript budget, with headroom

- Status: Accepted, 2026-11-23. The guest menu's own first-load JavaScript had grown to 26.1 KB gzip (limit 25 KB in `tests/e2e/guest-menu.spec.ts`) after the status poll, promo banners, waiter-call requests, substitutes and analytics landed, with calories and suggestions still to come. Now 20.0 KB (7.7 KB loaded later, limit 10). No limit was raised.
- Rules for every future guest feature:
  1. **Everything new on the guest path is lazy or server-rendered.** The first-load own JS target is **22 KB or less** (the test's hard limit stays 25 KB, so a 3 KB reserve is for emergencies, not for features). Idle-loaded code stays under 10 KB. Check with the budget test and the per-chunk numbers it prints before merging.
  2. **Server first.** Text, notes, banners and badges that need no browser state are rendered by a server component from data already in the page; only the part that needs the browser (a close button, a toggle) is a small client component taking the server markup as `children` (example: `promo-banner.tsx` and `promo-shell.tsx`).
  3. **Load on need, not at idle.** Prefer an import on the tap, on the first keystroke (search folding), when the cart gets its first line (order view and send area), or after a delay the feature allows (the status poll starts 3 s after load, its first answer still due at 10 s). Idle loading is for what must work with no signal and only for tables that can order (the waiter's question). The dish sheet loads on the first move, touch or scroll.
  4. **A stub in the main bundle, the logic behind a dynamic import.** Shared state or a cheap check stays (`call-waiter-state.ts`, `pending-request-key.ts`); parsing, retries and UI move out.
  5. **No new icon library calls on the guest path.** `guest-menu/icons.tsx` draws the Lucide shapes the guest pages use (ISC licence) without lucide-react's factory (about 1.6 KB). Add a shape there; do not import `lucide-react` into a guest client file.
  6. **Shared files keep client and server code apart.** A client file must not import a module that carries server-only builders (`view-model.ts` is imported for two small helpers only; check the chunk if that grows).
  7. **No supabase-js on the guest path** (the test fails on any chunk with "supabase" in its name).
- What moved (gzip, approximate): the order view and its send area (about 3 KB) load when the cart has a line; icons without the factory (1.3 KB); the waiter's question and its request bookkeeping (1.2 KB) and the status poll (0.9 KB) behind dynamic imports; the search folding table (0.7 KB) on the first keystroke; promo banner text on the server (0.5 KB). The dish sheet now waits for the first move, touch or scroll instead of idle time.
- Consequences and limits:
  - The budget test opens the menu **without a table token**. A page with a table also loads the waiter's question at idle (about 1.3 KB more later); keep that in mind when adding idle code, or extend the test with a table page.
  - The rail's lines (`line-row.tsx`) now load with the rail on a desktop (later bucket); the order view's `CartView` is separate.
  - Still heavy: the section headings' reveal animation (`SplitText`, 2.1 KB), the shared UI helpers (1.4 KB), the cart store and rules (2 KB), the guest i18n provider. Next candidates if the budget tightens: load the heading reveal only for headings below the fold, and the cart store only once a dish is added.

## ADR-081: "Can't make" on a dish already ordered (spec A, fallback)

- Status: Accepted, 2026-11-23. Migration `20261123310000_cant_make`.
- Context: some problems are found only at cooking time (an ingredient that is missing, a broken oven). Until now the kitchen had to call the waiter, and the waiter cancelled the line by hand and told the guest. ADR-076 handles an ingredient that is *known* to be out; this is the fallback for everything else.
- Decision: **one action by the kitchen** (`api.cant_make_item(order_item_id)`, button "Can't make" on a ticket line with a confirm step) does four things in one transaction:
  1. Cancels the rest of that line through the same rule as `api.cancel_order_item` (void slip, line total zero, order total recomputed, history row). The body now lives once in `private.cancel_order_item_core`; `api.cancel_order_item` calls it with its old roles, so the lock order of ADR-064 (order, ticket, line) and every earlier test still hold. The history row carries the reason code `cant_make`; if it was the last line the order is cancelled with the same code.
  2. Marks the line (`order_items.cant_make_at`). The guest's order page already reads its lines through RLS, so it shows "Sorry, this dish isn't available right now. Our chef suggests: …" on the next realtime refresh or poll. It never says "out of stock".
  3. Tells the waiters: `api.table_alerts` (ADR-071) gets rows with reason `cant_make` (dish, quantity) that stay until a waiter taps "Told the guest" (`api.ack_cant_make`, sets `cant_make_ack_at`), shown on the table panel and in the floor strip; and one `table.alert` outbox row per press (key: line and cancelled quantity) goes to the Telegram chats and phones in each recipient's language. The minute job is not involved, so there is no delay and no second row.
  4. Leaves the bill right: nothing else is needed because the bill reads `line_total`; a **paid order is refused** (`order_paid`), so a closed bill never changes.
- Who may press it: owners, managers, waiters and **kitchen** logins. This adds the kitchen role to the people who may cancel a line (`api.cancel_order_item` stays owner, manager, waiter), because the button is on the kitchen screen. Food whose ticket is already served stays a manager's decision, as for any cancellation. Guests and other cafés get `forbidden`.
- Alternatives (`api.cant_make_alternatives(order_item_id) -> uuid[]`, at most 3, callable by the order's guest session and by staff of the café): rules only. Same section first, then the same dish type (`items.item_type`, ADR-077); only dishes that can be ordered now (on the published menu, active, section active and open, not stop-listed, not blocked by an ingredient outage), never one already on the order, and none that needs a choice (a required option group), so one tap is enough. Ordered by how often the café sold it in 60 days, then by name. The guest page names them from the menu it already has (a small id -> name and price map from the server) and each button puts the dish in the cart and opens the menu: **nothing is ordered by itself**.
- Tolerates a database without the migration: the kitchen probes `order_items.cant_make_at` and hides the button; the guest and waiter screens read the new columns as absent.
- Guest page budget: the note is a lazily loaded client file on the order page only; the menu page's first-load JS is unchanged (20.0 KB).
- Not done: a quantity picker (the button cancels what is left of the line; use the waiter's cancel for part), an alert for a dish the kitchen can't make before it is ordered (that is ADR-076 and the stop list).

## ADR-082: Approximate calories, "Chef's pick" and guest filter chips (spec 4.2)

- Status: Accepted, 2026-11-23. Migration `20261123320000_calories_tags`.
- Context: guests ask "how heavy is it?" and "what is vegetarian, spicy or without nuts?". The ingredients (ADR-076) already carry `kcal_per_100g` and each dish has recipe lines, so a number can be derived instead of typed. A wrong number is worse than none, and allergen facts are the venue's responsibility.
- Decision, calories:
  1. **The rule** (`private.item_kcal_detail`): kcal = sum over the dish's recipe lines of weight × `kcal_per_100g` / 100. Weight is the quantity for `g`, the quantity for `ml` (treated as grams) and quantity × the new optional `ingredients.grams_per_piece` for `pcs`. **Only when every line has both** a calorie value and a usable weight; otherwise there is no number (never a partial total). Rounded to the nearest 10; a total that rounds to 0 is not shown. Per portion only, no per-100 g. Substitutes are not applied (the number is for the normal recipe).
  2. **Computed at publish time** into the published snapshot: `private.publish_menu_core` is redefined (only change: `"kcal"` in each dish, present only when there is a number), so the number reaches guests after Publish like every other menu change, and `api.public_menu` and its outage overlay pass it through unchanged.
  3. **Owner side**: `api.item_kcal(item)` returns the live number and the lines that block it (`kcal` = no calories, `weight` = no piece weight); the ingredients panel shows "Guests will see ≈ N kcal per portion after you publish" or "Add calories for X to show a number". `api.set_ingredient_kcal(ingredient, kcal_per_100g, grams_per_piece)` (owner and manager, definer, checked) edits the two values; `api.save_ingredient` stays as it was (it needs the whole ingredient and does not know the piece weight). The change applies to every dish using the ingredient.
  4. **Guest**: "≈ 620 kcal" (always with ≈, in the guest's language) in the dish sheet only, never on the list; shown only when the snapshot has it.
- Decision, tags and filters:
  1. `chefs_pick` joins the allowed tags (`api.save_item`'s list, redefined from its latest definition in `20261120090000_dish_allergens`; nothing else changed), the admin schema and chips, and the guest tag labels.
  2. **Chips** in the existing lazy filter dialog (button renamed "Filters" with a count): vegetarian (a vegan dish counts), spicy, new, chef's pick and "contains nuts" (derived from the venue's `nuts` or `peanuts` allergens; a dish with no allergens listed never matches). Chips combine (a dish must match all), filtering is client-side over the loaded menu, a "Show all" line under the search resets them. Not remembered between visits (unlike the allergy choice, which is about the person).
  3. **Allergen responsibility**: "Allergen information is provided by the venue." sits in the dish sheet's allergen line and in the filter dialog's note.
- Tolerates a database without the migration: the guest page simply has no `kcal` and no chip for an unused tag; the editor probes `ingredients.grams_per_piece` and hides the calorie fields; saving `chefs_pick` before the migration is refused by the old list (the chip is shown but the save fails with the usual message).
- Guest page budget: the chips, their texts and the kcal formatting are in the lazy dialog and the lazy sheet; first-load JS went from about 20.2 KB to 20.4 KB (the filter state, the small matching function and the status line).
- Not done: calories per 100 g for the guest, modifiers' calories (option lines are not part of the number), per-ingredient nutrition beyond kcal.

## ADR-083: "No allergens" is a statement the owner makes (spec 4.2)

- Status: Accepted, 2026-11-23. Migration `20261123340000_allergen_review`.
- Context: an empty `items.allergens` list meant "nobody entered it", so a guest with an allergy could not tell "this dish has none of the 14" from "unknown". Spec 4.2: allergen tags show only what the venue confirms, with a note that the venue is responsible.
- Decision:
  1. **Data**: `items.allergens_confirmed boolean not null default false` ("the owner reviewed this dish's allergen information"). Backfill: true where the list is not empty. `api.save_item` (latest definition, only this key added): a non-empty list sets it true; the key `allergens_confirmed` sets it as given; a list that is emptied without the key resets it to false (removing the last tick must never become a claim of "none"); a missing key keeps the stored value. No separate bulk function and **no "mark everything reviewed"** action: it would make claims the owner never checked. `private.publish_menu_core` (latest definition, only this key added) writes `allergens_confirmed` per dish, true also when the list is not empty (rows written by scripts that bypass `save_item` stay consistent). Older snapshots have no key: the guest treats a dish with a list as confirmed, anything else as not.
  2. **Owner editor**: next to the allergen toggles a checkbox "Reviewed: this dish contains none of the 14 allergens" (disabled while any allergen is ticked, because the list already speaks); ticking an allergen implies review, un-ticking the last one takes it back. Unreviewed dishes carry a neutral "Allergens not reviewed" chip in the list, and a filter button "Allergens not reviewed: N" (per section) shows only them.
  3. **Guest**: confirmed + empty list reads "No allergens declared by the venue." (never "safe", never "free of"), confirmed + list is as before, not confirmed keeps "Allergens aren't listed for this dish. If you have an allergy, tell your waiter." Every variant is followed by "Allergen information is provided by the venue."
  4. **Guest allergy filter**: unchanged in shape and the safer of the two options. A dish that is not confirmed is **kept visible and marked "Allergens not listed. Ask your waiter."** (never treated as safe, never silently hidden: a hidden dish the guest would have been fine with is a worse failure than a clear mark, and the waiter line is already there). A confirmed empty dish is not marked (the venue says none). The "contains nuts" chip needs a listed `nuts`/`peanuts`, so it never matches a dish without a list. The filter button appears when any dish is confirmed or has a list.
  5. **Showcase café** (`scripts/seed-showcase.mjs`, idempotent): the dishes with an intentionally empty list that are plain (espresso, tea, juice, lemonade, fries, grilled vegetables) are saved as reviewed; khorovats stays unreviewed so both states can be shown. The seed now sends `allergens_confirmed` on every `save_item` (otherwise a re-run would reset it). **Blanca is not touched**: her real dishes need the owner's own review.
- Tolerates a database without the migration: the editor probes the column (`allergenReviewSupported`) and hides the checkbox, chip and filter; the guest menu has no flag and behaves as before; the key sent to the old `save_item` is ignored.
- Guest page budget: a boolean in the view model, one extra branch in the matcher and one message key (in the lazy sheet); first-load growth well under 0.1 KB.
- Not done: bulk review, a per-allergen "may contain traces" level, an expiry on the confirmation.
