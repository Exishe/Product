# Internationalisation: Armenian, Russian, English

Armenian is the default and the reference language, not a translation of English. Russian and English are equals for guests. Every string a person reads comes from translation files or translation tables, never from code.

## Who sees which language

| Surface | Language comes from | Default |
|---|---|---|
| Guest menu and order status | Guest's choice (switcher), then browser `Accept-Language` matched against the location's `guest_locales` | Restaurant `default_locale` (hy) |
| Waiter app, admin | `members.locale` | hy |
| Kitchen screen, item names on tickets | `locations.kitchen_locale` | hy |
| Telegram messages | `notification_channels.locale` | hy |
| Menu content | `*_translations` rows; order lines keep a copy of all three | — |

A tourist orders "Khorovats" in English, and the kitchen ticket says «Խորոված»: order lines store `name_i18n` with every language. The smoke test checks it. The guest's free-text note is shown as typed, marked with its language.

## UI strings

- next-intl with `messages/hy.json`, `messages/ru.json`, `messages/en.json`, using ICU message syntax. Keys are namespaced by screen (`guest.cart.submit`, `kitchen.ticket.void`).
- No literal UI text in components. An ESLint rule (`react/jsx-no-literals` or the next-intl plugin) fails CI on new hard-coded strings.
- Guest pages use a locale segment, `/{locale}/m/{restaurant}/{location}`, so a shared link opens in the same language. Public menus will be indexable later, for Stage 3 own-site ordering. The QR entry `/t/<token>` picks the locale and redirects there.
- Staff and admin pages have no locale in the URL; the locale comes from the member's setting. Phase 2 confirms that next-intl handles both routing modes in one app.
- Plurals. Checked in Node and in Chromium: Armenian has the categories `one` and `other`, and `0` counts as `one`. Russian has `one`, `few`, `many`, `other` (1 блюдо, 2 блюда, 5 блюд, 21 блюдо). In Armenian, a noun after a number stays singular («3 ուտեստ», not «3 ուտեստներ»), so most Armenian plural messages need one form. Where "no items" reads differently, use an explicit `=0` branch in every language.

## Menu content

- Stored in the five `*_translations` tables, one row per language (`data-model.md`).
- Fallback chain: requested language → restaurant default → any language present. Guests never see an empty name. The admin shows a completeness meter per language and highlights missing rows.
- AI translation. After the photo import, or when the owner adds a dish in one language, Claude drafts the other two. Those rows get `source = 'ai'`, and `api.publish_menu` refuses to publish until the owner has marked them reviewed.
- Translation rules given to Claude:
  - Armenian dishes keep their name, transliterated, with a short gloss in Russian and English: «Խորոված» → "Хоровац (шашлык)" / "Khorovats (Armenian barbecue)". Glosses appear only in the first-line description, never in the name, so names stay short on tickets.
  - International dishes use the established name in each language: "Цезарь", "Caesar salad", «Ցեզար աղցան».
  - Armenian output follows the `hy-writer` rules: reformed spelling, Armenian punctuation, no Russian calques.
  - Russian output is natural menu Russian, not word-for-word.
  - Prices and portions are never translated; they're numbers, formatted by us.
- Stage 2: a per-restaurant glossary ("our «Տոլմա» is always «Толма» and "Tolma"") fed into the prompt.

## Formatting: don't trust the browser for Armenian

Checked on 9 Nov 2026 by formatting the same values in Node 22 (full ICU) and headless Chromium 153:

| Formatter | Node, `hy-AM` | Chromium, `hy-AM` |
|---|---|---|
| `NumberFormat` AMD currency | `1500 ֏` | `AMD 1,500` (English fallback) |
| `DateTimeFormat` medium | `13 նոյ, 2026 թ., 22:45` | `Nov 13, 2026, 10:45 PM` (English fallback) |
| `PluralRules` | supported | supported |
| `RelativeTimeFormat`, `ListFormat`, `Collator` | supported | not supported |

Chromium lacks Armenian locale data for everything except plural rules, and Chrome is what most Android guests use. So we ship our own small formatting module, used in both server and client code:

| Value | hy | ru | en |
|---|---|---|---|
| Price | `1 500 ֏` | `1 500 ֏` | `AMD 1,500` |
| Large number | `12 450 000` | `12 450 000` | `12,450,000` |
| Time | `22:45` | `22:45` | `22:45` (24-hour; we're in Yerevan) |
| Date in lists and reports | `13.11.2026` | `13.11.2026` | `13 Nov 2026` |
| Relative time | from message files: «5 րոպե առաջ» | «5 минут назад» | "5 min ago" |

Thousands separators and the space before ֏ are no-break spaces (U+00A0), so a price never wraps across lines. Amounts are whole drams, so no decimals ever show.

## Armenian typography rules for the UI

- `<html lang="hy">` on Armenian pages. A mixed-language fragment, such as an Armenian dish name inside an English page, gets its own `lang` attribute, so screen readers and hyphenation behave.
- Punctuation: ։ (U+0589) ends a sentence, ՝ (U+055D) and ․ (U+2024) mark pauses, the question mark ՞ sits on the stressed vowel of the questioned word («Պատվիրե՞լ»), and quotes are « ». A Latin colon is fine inside times (`22:45`).
- Grammar traps that turn up in UI strings: the article becomes ն before a vowel («Պատվերն ընդունված է։», not «Պատվերը ընդունված է»); a noun after a number stays singular; buttons use the infinitive and say what happens («Պատվիրել», «Կանչել մատուցողին», «Հաստատել»).
- Register: guest pages use lowercase «դուք» (website style). Staff screens use short imperatives with no pronouns.
- AI output and owner input: when a Latin `:` ends an Armenian sentence, the admin suggests «։». It doesn't silently change it.
- Russian: «вы» lowercase in the UI, «ё» where it changes meaning, « » quotes, no bureaucratic phrasing.

## Fonts

The font must cover Armenian, Cyrillic and Latin, with weights from regular to bold or black for the kitchen screen. Checked against Google Fonts metadata on 9 Nov 2026: of 1,959 families, **only 8 include an Armenian subset**:

| Family | Cyrillic | Use |
|---|---|---|
| Google Sans | yes | Text and UI candidate: one variable family for all three scripts |
| Noto Sans Armenian | no (pair with Noto Sans) | Safe fallback |
| Noto Serif Armenian | no (pair with Noto Serif) | Possible display or menu-heading face |
| Handjet, Tiny5, Tiny5 Duo | yes | Display novelty, not for body text |
| Iosevka Charon, Iosevka Charon Mono | yes | Monospace |

Phase 3 picks the type pairing, possibly adding a licensed Armenian face outside Google Fonts (Mardoto, GHEA family), and checks each license. Two rules apply whatever we pick:

1. Every family in the stack must contain Armenian glyphs. If the browser silently falls back to a system font mid-word, the result looks broken.
2. Armenian runs visually smaller and longer than Latin at the same size. Buttons and table cells are designed for 40 % longer labels, and Phase 3 checks every screen with real Armenian and Russian copy, not lorem ipsum.

## Search

Guests may type «խորոված», "хоровац" or "khorovats". The menu is a small JSON document, so search runs in the browser:

1. Normalise the query and every name: lower case, Unicode NFC, strip punctuation.
2. Map Armenian and Cyrillic to one Latin skeleton: խ→kh, ծ→ts, ժ→zh, ղ→gh, ու→u, և→ev; х→kh, ц→ts, ж→zh, ч→ch, ш→sh, щ→shch; plus the plain letters.
3. Match on substring of the skeleton across all three names, so "khorovats" finds «Խորոված» and "Хоровац".

Postgres has ICU collations `hy-AM-x-icu` (checked locally) for admin lists sorted by Armenian name. Chromium's `Intl.Collator` lacks Armenian, so client-side sorting uses the stored `sort` order, never alphabetical sorting.

## Quality checks

- Playwright runs the main guest, waiter and kitchen screens in hy, ru and en at 360 px, 768 px and 1280 px, and fails on horizontal overflow or truncated buttons.
- `messages/hy.json` goes through the `hy-writer` checker (punctuation, spelling dictionary, calques) in CI.
- A native Armenian speaker reads every Armenian UI string, and every system text a guest or owner sees, before the first café goes live.
